## 详细发现

### 1. daily_review.py 存在硬编码路径与跨环境兼容性问题
- **位置**：`scripts/daily_review.py` 第18-20行
- **严重程度**：🟡 警告
- **描述**：`REPO_PATH` 从 `auto_fix._REPO_PATH` 获取，但 `auto_fix.py` 中的 `REPO_PATH` 默认使用环境变量 `REPO_PATH` 或基于 `__file__` 的相对路径。在cron/不同工作目录下运行时，路径解析可能出错。`review_state.py` 中更是直接硬编码 `/root/.hermes/hermes-agent/remote-test`。
- **建议修复**：统一使用环境变量 `REPO_PATH`，并在启动时验证路径存在性；所有模块从同一配置源读取路径。

### 2. auto_fix.py 的 SEARCH/REPLACE 匹配逻辑存在边界风险
- **位置**：`scripts/auto_fix.py` 第60-97行
- **严重程度**：🟡 警告
- **描述**：`apply_search_replace` 使用 `content.count(search)` 判断唯一性，若代码中存在注释或字符串中偶然包含相同片段，会导致匹配不唯一而失败。此外，`search_stripped` 和 `replace_stripped` 仅去除尾部换行，未处理首尾空白差异，可能导致匹配失败。
- **建议修复**：引入更鲁棒的匹配策略，如要求SEARCH片段前后至少包含一行上下文（3-5行），或使用AST级别的替换（对Python文件）。

### 3. review_state.py 硬编码绝对路径
- **位置**：`scripts/review_state.py` 第13行
- **严重程度**：🔴 严重
- **描述**：`REPO_PATH = Path("/root/.hermes/hermes-agent/remote-test")` 是写死的绝对路径，在其他机器或Docker环境中直接无法运行。
- **建议修复**：改为 `REPO_PATH = Path(os.environ.get("REPO_PATH", Path(__file__).resolve().parent.parent))`，与 `auto_fix.py` 保持一致。

### 4. extract_legal_provisions_regex.py 正则模式复杂度与维护性
- **位置**：`scripts/extract_legal_provisions_regex.py` 第34-85行
- **严重程度**：🟡 警告
- **描述**：`_PATTERNS` 列表包含5个复杂的正则模式，嵌套了 `_CN_NUM_PATTERN` 和 `_CN_NUMS` 变量，可读性较差。模式B（简写格式）的前置否定断言 `[^条款项...]` 长达数十个字符，维护困难。此外，模式C的 `[^《》]{0,40}?` 非贪婪匹配可能在某些长文本中失效。
- **建议修复**：将每个模式拆分为独立的命名函数，添加单元测试覆盖边界案例；对模式B的前置字符类进行简化或注释说明。

### 5. legal_provision_extractor.py 存在重复造轮子
- **位置**：`scripts/legal_provision_extractor.py`
- **严重程度**：🟢 建议
- **描述**：该文件与 `extract_legal_provisions_regex.py` 功能高度重叠（均提取法律条文），但使用不同的输出格式和正则策略。`parse_guiding_cases_llm_v2.py` 中同时使用两者，增加了认知负担和维护成本。
- **建议修复**：考虑将两个提取器合并，或明确分工（如 `extract_legal_provisions_regex.py` 负责原始文本粗提取，`legal_provision_extractor.py` 负责CSV记录的字段级提取和格式标准化）。

### 6. generate_ontology_viz.py 的 HTML 模板内嵌 JavaScript 存在 XSS 风险
- **位置**：`scripts/generate_ontology_viz.py` 第169-316行
- **严重程度**：🟡 警告
- **描述**：`HTML_TEMPLATE` 使用 `.replace("{nodes}", ...)` 和 `.replace("{edges}", ...)` 插入JSON数据。虽然当前数据来自受控的YAML文件，但如果未来YAML内容可被用户输入污染，未转义的 `"` 或 `</script>` 可能破坏HTML结构。
- **建议修复**：使用 `json.dumps(..., ensure_ascii=False)` 并配合HTML转义，或改用Jinja2模板引擎进行安全渲染。

### 7. apply_user_confirmation.py 的 merge 逻辑缺少冲突解决策略
- **位置**：`scripts/apply_user_confirmation.py` 第105-125行
- **严重程度**：🟡 警告
- **描述**：`merge_branch_to_main` 在merge失败时直接 `merge --abort` 并返回错误，没有尝试自动解决简单冲突（如双方在同一文件不同位置修改）。对于自动化流程，这可能导致用户确认后无法自动合并，需要人工介入。
- **建议修复**：在abort前尝试 `git merge --strategy-option=ours` 或基于文件级别的冲突检测自动选择；至少将冲突文件列表返回给用户。

### 8. text_compressor.py 的争议焦点提取可能过度匹配
- **位置**：`scripts/text_compressor.py` 第58-94行
- **严重程度**：🟢 建议
- **描述**：`extract_disputed_issues` 中的 `section_titles` 正则 `[一二三四五六七八九十、]{1,5}([^
]{5,60}?)(?:。|；)` 可能将普通列举项误判为争议焦点。`unnumbered_patterns` 中的 `关于([一-龥]{5,40}?)的认定` 也可能匹配非争议内容。
- **建议修复**：增加后置验证，如要求提取的issues在judgment_reason中出现在"争议焦点"、"本院认为"等关键词附近；或引入轻量级分类器过滤。

### 9. parse_guiding_cases_llm_v2.py 的并发控制缺少速率限制
- **位置**：`scripts/parse_guiding_cases_llm_v2.py` 第173-177行
- **严重程度**：🟢 建议
- **描述**：`ThreadPoolExecutor(max_workers=2)` 虽然限制了并发数，但没有显式的速率限制（rate limiting）。对于API调用，2个并发在高峰时段仍可能触发限流。
- **建议修复**：增加 `requests-per-second` 限制，或在重试逻辑中加入指数退避的 jitter。

### 10. patches/2026-04-30_all_changes.patch 文件体积过大
- **位置**：`patches/2026-04-30_all_changes.patch`
- **严重程度**：🟢 建议

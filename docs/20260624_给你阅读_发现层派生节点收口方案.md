# 20260624_给你阅读_发现层派生节点收口方案

## 1. 这次要解决的核心问题

当前 `discovery` 层已经开始从“无差别复制节点”收口到“优先引用正式实体”，但还有一部分对象需要进一步明确边界：

- `LegalProvisionElement`
- `SentencingCircumstance`
- `EvidenceChain`
- `ArgumentOutcome`

这 4 类对象并不完全一样。

如果继续把它们全部当成普通 `DiscoveryNode` 来处理，会有两个问题：

- 一部分其实和 `base` 已有正式实体高度重合，应该优先复用
- 另一部分其实不是正式本体实体，但会在多个发现记录中反复出现，应该在文书内收口成稳定的派生节点

所以这次不是简单问“要不要保留 `DiscoveryNode`”，而是要回答：

- 哪些对象应复用 `base`
- 哪些对象应保留为 `discovery` 层派生节点
- 哪些对象甚至不该继续做成节点

## 2. 总体结论

### 2.1 LegalProvisionElement

建议采用：

- 部分复用 `base`
- 部分保留为 `discovery` 派生节点

原因是：

- `base` 里的 `LegalProvisionElement` 更偏“正式法条要件”
- `discovery` 里的 `LegalProvisionElement` 往往已经带有“本案适用解释、阈值化表达、结论化描述”

也就是说，这两者并不总是同一层语义。

### 2.2 SentencingCircumstance

建议：

- 正式收口为“文书级 canonical discovery derived node”

原因是：

- 它不是原始解析事实
- 它是围绕本案裁判尺度形成的派生评估对象
- 同一语义会在多个发现记录中反复出现

### 2.3 EvidenceChain

建议：

- 也收口为“文书级 canonical discovery derived node”

原因是：

- 它本质上是推理中形成的证据链结构
- 不属于 `base` 正式实体
- 但同一证据链也会在多个发现记录里重复被提到

### 2.4 ArgumentOutcome

建议：

- 优先降为结果值 / 枚举值 / 关系属性
- 不建议继续作为普通 `DiscoveryNode`

原因是：

- 当前它主要只是“采纳 / 驳回”这类有限结果
- 更像状态值，而不是需要长期保留的实体对象

## 3. 为什么 LegalProvisionElement 不能一刀切

这是这次最容易误判的一类。

### 3.1 可以直接复用的情况

如果 `discovery` 里的 `LegalProvisionElement` 只是对 `base` 要件的轻度改写，例如：

- 标题式改写
- 同义表达
- 前缀补充说明

但本质上仍然指向同一个法条要件，那么应直接复用 `base` 中那份正式节点。

### 3.2 不适合直接复用的情况

如果 `discovery` 里的 `LegalProvisionElement` 已经明显带了：

- 本案适用结果
- 数额阈值
- 裁判中的解释性语言
- 结论化表达

那么它已经不只是“法条要件本身”，而是：

- 法条要件
- 加上本案适用后的解释

这类对象如果直接并回 `base`，会把“正式规范层”和“个案解释层”混在一起。

### 3.3 更合理的理解方式

建议把它拆成两层：

- `base LegalProvisionElement`
  - 表示正式规范要件
- `discovery AppliedLegalProvisionElement`
  - 表示在当前文书里被推导、解释、阈值化后的要件表达

这意味着：

- 能强匹配到规范要件的，复用 `base`
- 不能强匹配、或已经明显带案情解释的，保留为 `discovery` 派生节点

## 4. 为什么 SentencingCircumstance 适合文书级收口

量刑情节和事实、证据不同，它天然带有很强的“个案推理”属性。

例如：

- 主动缴纳罚金
- 从犯
- 坦白
- 认罪认罚
- 参与程度更深

这些对象虽然不一定都在 `base` 中以统一方式出现，但在同一份文书里通常会反复参与不同发现记录的推理。

如果每条发现记录都各造一份，会带来两个问题：

- discovery 内部同语义节点重复
- 后续很难判断某条裁判尺度分析究竟引用的是不是同一个量刑情节

所以更合理的模型是：

- 文书内只保留一份 canonical `SentencingCircumstance`
- 各 discovery record 只引用它

## 5. 为什么 EvidenceChain 也适合文书级收口

证据链不是原始事实，而是推理过程中形成的结构化组合。

它通常回答的是：

- 哪几条证据共同证明了某个事实
- 哪条链条支撑了某个从轻或从重情节

这种对象：

- 不适合并到 `base`
- 但也不该在 discovery 内无限重复创建

所以它最适合留在 `discovery` 层，但做“文书内 canonical 收口”。

## 6. 为什么 ArgumentOutcome 更适合降级

`ArgumentOutcome` 当前主要体现：

- 采纳
- 驳回

从语义上看，它更像：

- 某个论点、诉求或抗辩的处理结果

而不是一个值得长期独立存在的知识实体。

所以更合理的做法是：

- 让它成为关系上的结果值
- 或成为有限枚举值

只有在以后明确要围绕“结果类型”做复杂聚合、比对、统计时，才需要把它重新升级成受控节点。

## 7. 建议的最终边界

### 7.1 应复用 `base` 的

- `ArgumentPoint`
- `DisputeFocus`
- `LitigationClaim`
- 部分 `LegalProvisionElement`

### 7.2 应保留为文书级 canonical discovery derived node 的

- `SentencingCircumstance`
- `EvidenceChain`
- 部分带个案解释色彩的 `LegalProvisionElement`

### 7.3 应降为值或属性的

- `ArgumentOutcome`

## 8. 这套边界的收益

如果按这个方向继续收口，`discovery` 会更稳定：

- 和 `base` 的重复会进一步减少
- discovery 内部的重复派生节点会减少
- 同一文书里的推理对象会有更稳定的身份
- 后面做 diff、子图、更新、跨记录追溯都会更容易解释

## 9. 推荐推进顺序

建议按以下顺序继续：

1. 先补 `LegalProvisionElement` 的三档判定
2. 再正式把 `SentencingCircumstance` 做成文书级 canonical derived node
3. 再把 `EvidenceChain` 做成文书级 canonical derived node
4. 最后把 `ArgumentOutcome` 降为枚举值或关系属性

## 10. 本文结论

这 4 类对象不能再用同一种方式处理。

更合理的最终方案是：

- `LegalProvisionElement`：部分复用、部分派生
- `SentencingCircumstance`：文书级 canonical discovery derived node
- `EvidenceChain`：文书级 canonical discovery derived node
- `ArgumentOutcome`：优先降为值或属性

这样既能继续坚持“本体统一”，也不会把 discovery 里的个案推理语义硬塞回 `base`。

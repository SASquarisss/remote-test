本文档用于沉淀当前 `remote-test` 项目在现有架构基础上引入 Neo4j 的工程设计方案，并进一步细化到接口设计稿层级。

2. Neo4j 引入后的总体架构
3. ID 设计与图谱分层策略

- 当前阶段不要求引入向量化，仅为后续 GraphRAG 留扩展位。

## 2. 当前项目现状与接入边界

### 2.1 当前后端解析主链

当前后端解析主入口位于 `backend/parser.py` 的 `parse_text()`，核心链路为：

`raw_text -> build_row_from_text() -> build_llm_input() -> call_llm() -> enrich_graph_output() -> kg_convert()`

对应现状：

- 当前原始文书解析仍然是“整篇文本直接调用大模型 API”。
- 当前并没有引入 chunk 参与解析，也没有 chunk 级召回。
- 当前前端主图渲染依赖解析结果中的 `json_result`、`nodes`、`edges`。
- 当前测试态刷新恢复依赖 `/api/test-data`。
- 当前正式保存依赖 `/api/save` 写入本地 JSONL 与 cases index。

### 2.2 当前前端页面结构

#### Workspace

当前 Workspace 的主交互集中在 `TerminalPanel`：

- 解析
- 保存
- 质量分析
- 检索资产生成与编辑
- 深度思考（知识发现）
- 版本链切换

结论：

- Neo4j 写入操作优先复用 Workspace 中已有按钮区，不新建一个完全独立的大页面。
- Neo4j 不是先替代当前工作台内存态，而是先承担“结构化持久化层”和“后续检索层”。

#### Database

当前 Database 页面承担：

- 案例索引浏览
- 已保存案例详情查看
- 静态案例与保存案例混合浏览

结论：

- Database 适合作为 Neo4j 的浏览与运维入口。
- 后续由 Database 页面逐步优先消费 Neo4j 数据，比直接改 Workspace 更稳妥。

## 3. 设计原则

本轮 Neo4j 接入遵循以下原则：

1. **最小改动原则**
   - 不改变当前 LLM 解析主入口。
   - 不立即改造主图渲染来源。
   - 不废弃 JSONL 与 `/api/test-data`。

2. **双轨运行原则**
   - 当前本地 JSON / JSONL 继续作为工作台编辑态与回滚底座。
   - Neo4j 先作为并行持久化与结构化检索底座。

3. **分层写入原则**
   - 基础解析图、检索资产图、知识发现图不能混成一个无来源的大图。
   - 图谱中必须显式记录层级、来源、运行批次和版本信息。

4. **稳定 ID 原则**
   - 同一文书多次解析时，节点与关系要尽量保持稳定 ID。
   - ID 不能依赖数组顺序。

5. **溯源可追踪原则**
   - 后续所有结构节点应尽量能回指到文书原始文本块。
   - 本轮先做 chunk 切分与对齐，不做向量化。

## 4. Neo4j 引入后的总体架构

### 4.1 总体定位

Neo4j 的职责定义为：

- 承接结构化图谱持久化
- 承接案件级、跨案件级图关系组织
- 承接后续 GraphRAG 的图扩展基础
- 承接文本块与结构节点之间的溯源映射

当前不由 Neo4j 负责：

- 原始 LLM 解析入口
- 当前 Workspace 的即时主图渲染源
- 当前测试态缓存
- Embedding 生成

### 4.2 总体链路

建议链路如下：

1. 用户在 Workspace 输入原始文书文本
2. 后端调用现有 `parse_text()` 进行整篇解析
3. 在解析链中插入“文本块切分 + 结果对齐”中间步骤
4. 前端继续基于 `json_result` 渲染主图
5. 用户在 Workspace 触发“写入 Neo4j”
6. 后端根据当前图层与写入范围生成图数据库写入任务
7. Neo4j 存储：
   - 文书根节点
   - 文本块节点
   - 基础解析图
   - 检索资产图
   - 知识发现图
8. Database 页面逐步增加从 Neo4j 查询与运维的能力

## 5. ID 设计

## 5.1 文书主 ID

文书 ID 必须区分文书类型：

- 指导性案例：`GUIDE:<official_id>`
- 一般裁判文书：`CASE:<official_id>`

原因：

- 你已经明确两种文书类型会分别提供唯一 ID。
- 但两种类型之间可能重复，所以必须分域。

文书根节点建议统一标签：

- `:Document`

并保留属性：

- `doc_id`
- `doc_type`
- `external_id`
- `case_name`
- `source_text_hash`

## 5.2 节点 ID

### 5.2.1 基础原则

- 节点 ID 不依赖解析顺序。
- 节点 ID 基于“文书范围 + 语义签名”生成。
- 不要求把标签名写进 hash 内容，但必须在 Neo4j 层对每个标签独立建唯一约束。

### 5.2.2 局部节点

局部节点指默认属于单案范围的节点，例如：

- `Person`
- `Evidence`
- `Fact`
- `ArgumentPoint`
- `LitigationClaim`
- `ProceduralOpinion`
- `JudicialAssessment`
- `JudgmentResult`

建议公式：

`entity_id = hash(doc_id + normalized_core_fields)`

示例：

- 当事人：`hash(doc_id + name_norm + role_code + side_hint + org_hint)`
- 证据：`hash(doc_id + evidence_type + content_norm + submitted_by)`
- 事实：`hash(doc_id + fact_type + content_norm)`
- 争议焦点：`hash(doc_id + content_norm + focus_type)`

### 5.2.3 组织节点

当前原始数据几乎不包含社会信用代码，因此公司类组织的跨案全局合并不能过于激进。

建议：

- 法院 / 检察院 / 律所：优先按规范名称稳定建全局节点
- 普通企业 / 公司：当前先按企业名称归一化生成 ID

例如：

`organization_id = hash(organization_name_norm)`

但必须额外保留风险控制属性：

- `merge_status`
- `merge_confidence`
- `alias_names`
- `possible_same_as_candidates`

说明：

- 当前不能假设企业名称等于真实唯一实体。
- 后续如果拿到统一社会信用代码，再做全局合并升级。

### 5.2.4 法条与案由节点

对 `LegalProvision`、`CaseType` 等规范类节点，不需要把标签名写入 hash 内容。

建议：

- `LegalProvision.id = hash(law_name_norm + article + paragraph + item)`
- `CaseType.id = hash(code or level1 + level2)`

前提：

- Neo4j 对不同标签分别建立唯一约束，避免跨标签主键冲突。

## 5.3 关系 ID

关系也应使用业务主键，而不是依赖 Neo4j 内部关系 ID。

建议：

`relation_id = hash(from_id + relation_type + to_id + normalized_relation_attrs)`

关系必须显式记录以下属性：

- `relation_id`
- `relation_type`
- `relation_origin`：`explicit | implicit | derived`
- `source_pipeline`
- `source_run_id`

## 6. 图谱分层策略

当前图数据建议分为四层：

### 6.1 Base 层

来源：

- 初始解析
- 解析增强后的正式结构

作用：

- 作为案件基础结构图
- 支撑主图与基础类案分析

标记：

- `graph_layer = "base"`

### 6.2 Retrieval 层

来源：

- 检索资产生成逻辑

作用：

- 服务类案检索
- 服务链路说明、视角子图

标记：

- `graph_layer = "retrieval"`

### 6.3 Discovery 层

来源：

- 深度思考 / 知识发现

作用：

- 承接模型推理新增节点与关系
- 服务规则学习和知识扩展

标记：

- `graph_layer = "discovery"`

### 6.4 Community 层

来源：

- 未来社群发现、群组总结

当前状态：

- 暂不实施，但预留

标记：

- `graph_layer = "community"`

### 6.5 图层共性属性

所有节点和关系都建议统一增加：

- `graph_layer`
- `source_pipeline`
- `source_run_id`
- `workspace_id`
- `version_id`
- `active_flag`
- `created_at`
- `updated_at`

## 7. 文本块切分与解析结果对齐方案

这是本轮新增需求的核心部分，目标是：

- 不改变当前整篇文书调用大模型的解析方式
- 增加 chunk 层，以支持“从结构节点反查原文块”

## 7.1 接入点

最小改动接入点放在 `parse_text()` 内部：

1. `build_row_from_text(raw_text)` 之后执行 `segment_case_text(raw_text, row)`
2. 继续保持整篇文本解析，不改 `call_llm()`
3. `enrich_graph_output(output)` 之后执行 `align_output_to_chunks(output, text_chunks, row)`
4. 再执行 `kg_convert(output)`

这样做的优点：

- 不改现有 prompt
- 不改现有解析方式
- 不影响当前前端主图结构
- 仅在后端主链中新增两个轻量中间步骤

## 7.2 切分策略

建议采用“章节优先、段落次之、句子兜底”的分层切分策略。

### 7.2.1 一级切分：按业务章节

优先利用 `build_row_from_text()` 已识别出的结构区块：

- `basic_facts`
- `judgment_reason`
- `judgment_essence`
- `related_law`
- 其他显式段落

### 7.2.2 二级切分：按自然段

- 以连续换行作为自然段边界
- 保留段落顺序

### 7.2.3 三级切分：按句子兜底

对于超长段落：

- 按 `。；；\n` 等句边界切
- 初期不做 overlap

原因：

- 当前目标是“可回指原文块”，不是向量召回
- overlap 会增加对齐歧义

## 7.3 Chunk 数据结构

建议每个 chunk 至少包含以下字段：

```json
{
  "chunk_id": "CASE:12345:basic_facts:003",
  "doc_id": "CASE:12345",
  "section_type": "basic_facts",
  "seq": 3,
  "text": "……",
  "char_start": 1820,
  "char_end": 2016,
  "paragraph_index": 7,
  "chunking_version": "v1"
}
```

## 7.4 对齐策略

初期不用向量，对齐建议按规则分层匹配：

1. 精确包含匹配
2. 归一化后包含匹配
3. 同章节近似匹配
4. 找不到时退化到章节级来源，不强求单 chunk 命中

### 7.4.1 节点到文本字段映射建议

- `Fact` -> `content`
- `Evidence` -> `content`
- `ArgumentPoint` -> `argument_text`
- `JudicialAssessment` -> `assessment_text`
- `LitigationClaim` -> `claim_text`
- `ProceduralOpinion` -> `content`
- `JudgmentResult` -> `specific_judgment` / `reasoning`

## 7.5 返回与存储方式

初期不建议直接修改 `json_result` 内部结构，而是采用 sidecar 结构：

```json
{
  "json_result": { "...": "..." },
  "text_chunks": [ ... ],
  "source_alignment": {
    "Fact:abc123": [
      { "chunk_id": "CASE:12345:basic_facts:003", "score": 1.0, "match_type": "contains" }
    ]
  }
}
```

这样做的好处：

- 不破坏现有 `json_result` 结构
- 不影响前端现有渲染逻辑
- 不影响版本链、质量分析、保存逻辑
- 后续可逐步把 sidecar 投入 Neo4j

## 8. 前端页面交互设计

## 8.1 Workspace 页面

### 8.1.1 不建议新增独立 Tab

理由：

- Neo4j 写入本质是动作，不是长期浏览页
- 当前 Workspace 已有较多 Tab
- 再加一个大 Tab 会削弱“解析工作台”的主线体验

### 8.1.2 建议新增按钮位置

建议在当前保存按钮区域新增图数据库写入交互。

#### 位置 A：保存按钮旁边

用途：

- 写入当前案件基础图谱

建议按钮：

- `写入 Neo4j`
- `Neo4j 写入选项` 下拉

建议选项：

- `写入基础图谱`
- `写入基础图谱 + 文本块`
- `写入当前激活版本`
- `重新覆盖本案基础层`

#### 位置 B：检索资产区域

用途：

- 写入 retrieval 层

建议按钮：

- `写入检索层`

#### 位置 C：深度思考区域

用途：

- 写入 discovery 层

建议按钮：

- `写入发现层`
- `合并后写入发现层`

### 8.1.3 建议新增状态展示

在 Workspace 的状态栏或保存按钮附近显示：

- `Neo4j: 未写入`
- `Neo4j: 已写入基础层`
- `Neo4j: 已写入基础层 / 检索层 / 发现层`
- 最近一次写入时间
- 最近一次写入 run_id

## 8.2 Database 页面

Database 页面更适合加一个浏览与运维性质的 Tab。

### 8.2.1 新增右侧 Tab

建议在右侧区域新增：

- `图数据库`

作用：

- 展示当前案例的图数据库同步状态
- 展示各图层写入情况
- 支持从图数据库重载案例结构

### 8.2.2 图数据库 Tab 内容建议

- 当前案例 `doc_id`
- 同步状态
- 最近同步时间
- 已写入层级
- 可用操作：
  - `从图数据库重载`
  - `重新同步当前案例`
  - `查看图层差异`

### 8.2.3 Database 顶部筛选建议

增加数据来源筛选：

- `全部`
- `本地 JSON`
- `Neo4j`

## 9. 后端读写链路调整建议

## 9.1 近期不调整的部分

以下逻辑近期不建议切换为 Neo4j 主读：

- Workspace 首屏恢复仍走 `/api/test-data`
- Workspace 主图仍由 `json_result -> nodes/edges` 驱动
- 当前版本链仍以本地结构为准
- 当前 `save` 仍保留 JSONL

## 9.2 建议新增的写入链路

### 阶段 A：并行写入

- 解析不写库
- 用户显式点击“写入 Neo4j”后调用图数据库写入接口

### 阶段 B：保存后双写

- `/api/save` 成功后，可由后端同步或异步触发 Neo4j 写入
- 但前端显示结果仍然以本地保存结果为主

### 阶段 C：Database 优先消费 Neo4j

- Database 列表仍可从现有 `/api/cases` 补状态
- Database 详情逐步增加从 Neo4j 拉取的详情接口

### 阶段 D：Workspace 支持从图数据库重载

- 作为辅助入口，不作为默认入口

## 10. 建议新增 API

以下 API 只列设计建议，不代表本轮立刻实现。

## 10.1 Chunk 与对齐相关

### 10.1.1 解析并返回 chunk

`POST /api/parse-with-chunks`

用途：

- 返回现有解析结果
- 同时返回 `text_chunks` 与 `source_alignment`

请求：

```json
{
  "text": "原始裁判文书全文",
  "chunking": {
    "enabled": true,
    "version": "v1",
    "strategy": "section_paragraph_sentence"
  }
}
```

响应：

```json
{
  "row_id": "manual_1710000000",
  "case_name": "……",
  "json_result": {},
  "nodes": [],
  "edges": [],
  "score": 88,
  "issues": [],
  "text_chunks": [],
  "source_alignment": {},
  "chunking_meta": {
    "version": "v1",
    "chunk_count": 18
  }
}
```

说明：

- 也可以不单独拆新接口，而是在原 `/api/parse` 增加 `include_chunks=true` 参数。
- 从最小改动角度，更推荐“兼容扩展原 `/api/parse`”。

### 10.1.2 获取某案件 chunk

`GET /api/case/<row_id>/chunks`

用途：

- 给 DetailPanel 或后续查看器按案件拉取 chunk 和对齐信息

## 10.2 Neo4j 写入相关

### 10.2.1 写入当前案件基础图谱

`POST /api/neo4j/write-case`

用途：

- 写入基础解析图

请求：

```json
{
  "doc_id": "CASE:2024-001",
  "doc_type": "case",
  "row_id": "manual_1710000000",
  "case_name": "某某纠纷案",
  "raw_text": "……",
  "json_result": {},
  "parse_versions": [],
  "active_version_id": "v0",
  "write_options": {
    "graph_layer": "base",
    "include_chunks": true,
    "overwrite_scope": "doc_layer",
    "create_run": true
  }
}
```

响应：

```json
{
  "status": "ok",
  "doc_id": "CASE:2024-001",
  "graph_layer": "base",
  "source_run_id": "ingest_20260618_001",
  "written_nodes": 128,
  "written_relations": 241,
  "written_chunks": 21
}
```

### 10.2.2 写入检索资产层

`POST /api/neo4j/write-retrieval-layer`

请求：

```json
{
  "doc_id": "CASE:2024-001",
  "bundle_id": "bundle_xxx",
  "source_parse_version_id": "v1",
  "retrieval_bundle": {},
  "write_options": {
    "graph_layer": "retrieval",
    "reuse_existing_nodes": true
  }
}
```

### 10.2.3 写入知识发现层

`POST /api/neo4j/write-discovery-layer`

请求：

```json
{
  "doc_id": "CASE:2024-001",
  "source_parse_version_id": "v2",
  "discovery_run_id": "discovery_20260618_01",
  "discovery_payload": {
    "markdown": "……",
    "json_patch": {},
    "virtual_nodes": [],
    "relations": []
  },
  "write_options": {
    "graph_layer": "discovery",
    "merge_mode": "layer_isolated"
  }
}
```

### 10.2.4 查询当前案件写入状态

`GET /api/neo4j/case-status/<doc_id>`

响应：

```json
{
  "doc_id": "CASE:2024-001",
  "exists": true,
  "layers": {
    "base": true,
    "retrieval": true,
    "discovery": false
  },
  "last_runs": [
    {
      "graph_layer": "base",
      "source_run_id": "ingest_20260618_001",
      "updated_at": "2026-06-18T12:00:00Z"
    }
  ]
}
```

### 10.2.5 从 Neo4j 读取案件详情

`GET /api/neo4j/case/<doc_id>`

用途：

- 给 Database 页面逐步接入 Neo4j 读路径

支持参数：

- `graph_layer`
- `version_id`
- `include_chunks`
- `include_runtime_layers`

## 10.3 Neo4j 运维相关

### 10.3.1 重载当前案件

`POST /api/neo4j/reload-case`

### 10.3.2 比较本地 JSON 与图数据库差异

`POST /api/neo4j/diff-case`

## 15. 需要提前规避的潜在问题

## 15.1 公司名称误合并

当前没有统一社会信用代码，企业名称可能存在：

- 别名
- 简称
- 同名不同主体

建议：

- 初期不做过强跨案合并
- 预留人工校正与候选关系

## 15.2 关系删除语义不明确

同一案件多次解析后，如果某次不再产出某条关系，需要明确：

- 是物理删除
- 还是历史保留但当前版本失活

建议：

- 初期采用逻辑失活，不直接硬删除

## 15.3 基础图与发现图混淆

如果 discovery 层不隔离，后续会出现：

- 客观事实与推理结果混淆
- 类案检索污染

因此 discovery 必须独立图层、独立来源。

## 15.4 超级节点扩散

典型高风险节点：

- `LegalProvision`
- `CaseType`
- `Court`

后续如果从这些节点不受控扩散，GraphRAG 查询可能直接爆炸。

建议：

- 后续查询层显式限制扩散跳数与可扩散标签

## 16. 推荐落地顺序

建议按以下顺序推进：

### 阶段 1：最小可行能力

1. 在 `parse_text()` 中加入 chunk 切分
2. 生成 `text_chunks` 与 `source_alignment`
3. 保存到测试数据与正式保存结构中

### 阶段 2：基础写入能力

1. 新增 `write-case` 接口
2. 实现 `Document + Chunk + Base Layer` 写入
3. 在 Workspace 保存区增加 `写入 Neo4j`

### 阶段 3：图层写入能力

1. 支持 Retrieval 层写入
2. 支持 Discovery 层写入
3. 增加图层状态查询接口

### 阶段 4：Database 消费能力

1. Database 页面新增 `图数据库` Tab
2. 支持从 Neo4j 读取案例状态与详情
3. 支持差异查看与重同步

### 阶段 5：后续扩展

1. 向量化与相似合并
2. GraphRAG 混合检索
3. 社群发现与总结层

## 17. 本文档结论

本项目引入 Neo4j 的正确策略不是“立即替换现有主图工作流”，而是：

1. 保留当前 `json_result + 本地测试态 + JSONL` 的编辑与验证底座
2. 在后端解析链中增加 chunk 切分与对齐，建立原文溯源能力
3. 通过 Workspace 的按钮式交互逐步引入 Neo4j 写入
4. 通过 Database 的图数据库 Tab 逐步引入 Neo4j 读取与运维
5. 通过图层隔离、稳定 ID、运行批次和唯一约束，保证后续 GraphRAG 与知识发现扩展的可持续性

这条路径能最大程度减少对现有架构的破坏，同时为后续结构化检索、知识发现、类案分析和 GraphRAG 做好基础准备。

# 20260624_Neo4j唯一文书ID与分层更新策略方案

## 1. 文档目的

- 解决当前 `Workspace -> Neo4j` 写入链路中，文书唯一标识、分层更新、下游依赖稳定性、`retrieval` 写入门槛、`discovery` 可复现性等核心问题。
- 为后续实现提供一份可直接落地的工程方案，而不是停留在概念层面。

本文重点回答 5 个问题：

- 为什么现在会出现 `retrieval` 被前端拦截、但又希望“不做向量化也可以写入”。
- 为什么 `discovery` 在页面上可写，但 `Database` 里可能和已保存数据对不上。
- 为什么同一文书需要强制用户提供唯一文书 id，而不能继续依赖 `row_id`。
- 同一文书的初始解析、增量解析、检索层、发现层如何独立更新而不互相污染。
- 下游层如何稳定依赖上游层的实体 / 关系 id，而不会因为上游重写而全部断链。

## 2. 当前现场结论

### 2.1 retrieval 当前为什么被拦截

- 当前前端校验逻辑在 [TerminalPanel.js](file:///home/sxc/wendao/remote-test/visualization/ontology-refactored/src/components/TerminalPanel.js#L1962-L1979)。
- `buildRetrievalValidation()` 会同时产出 3 类问题：
  - 链路无效
  - `retrieval_text` 为空
  - 向量状态为 `pending / stale / failed`
- 随后前端又用“消息里是否包含 `pending / stale / failed`”来判定阻塞，见 [TerminalPanel.js](file:///home/sxc/wendao/remote-test/visualization/ontology-refactored/src/components/TerminalPanel.js#L2614-L2623)。
- 这意味着：当前“向量未完成”虽然只是 `warn`，但实际上也会被当成阻塞。

对当前案例 `CASE:manual_1780383896` 的真实统计结果：

- 总阻塞 / 提示数：`40`
- 其中：
  - 链路问题：`10`
  - 正文为空：`10`
  - 向量状态未就绪：`20`

结论：

- 你看到的“40 项阻塞问题”并不全是链路问题。
- 其中有一半其实只是“未做向量化”导致的 `embedding pending`。
- 这和你希望的产品语义冲突：你希望“不做向量化也可以写 Neo4j，但要提醒”。

### 2.2 discovery 当前为什么看起来“不稳定”

- 对 `CASE:manual_1780383896` 的当前已保存案例记录检查后发现：
  - 本地已保存的 `discovery_history` 数量：`0`
  - 但 Neo4j 当前 `discovery` 层中已有：
    - `DiscoveryRecord: 5`
    - `DiscoveryNode: 33`
    - `DiscoveryAnchor: 11`
    - 合计实体数：`49`

结论：

- 当前这条案例的 `discovery` 图数据已经写入过 Neo4j。
- 但这些 discovery 结果并没有持久化到当前保存记录中。
- 也就是说，Neo4j 里的 discovery 层和“当前已保存案例”并不总是同源。

这会直接导致两个问题：

- `Database diff` 无法稳定复现 discovery 差异，因为本地源数据为空。
- 之后如果做 `resync`，会出现“图里有，但本地没有”的状态漂移。

### 2.3 基础层是否真的重复了

对 `CASE:manual_1780383896` 的当前 Neo4j 状态检查结论：

- 当前只存在 1 个 `Document` 节点：
  - `doc_id = CASE:manual_1780383896`
- `base` 层当前活跃实体数与本地一致：
  - `56`
- `base` 层当前活跃关系总数：
  - `104`
- 各标签当前没有出现“同一 `doc_id` 下活跃重复”的现象。
- 当前库里确实存在多条 `IngestRun` 记录：
  - `base` 多次写入
  - `retrieval` 多次写入
  - `discovery` 多次写入

结论：

- **目前没有证据表明同一个 `doc_id` 下的 `base` 活跃数据真的重复了。**
- 你感知到“重复”，更可能来自以下几种情况：
  - 多次写入留下了多条 `IngestRun` 历史
  - 下游层仍在使用旧版本推导出的数据
  - 同一份文书未来若用不同 `doc_id` 写入，会形成“概念重复但主键不同”的双份文书

### 2.4 当前 schema 的一个结构性问题

- `Document.doc_id` 是唯一的，这是正确的。
- 但 `Document.graph_layer` 当前会被后一次写入覆盖，例如当前 `CASE:manual_1780383896` 的 `Document.graph_layer = discovery`。

结论：

- `Document` 不应该再承载“当前写入的是哪一层”这种易被覆盖的瞬时状态。
- 图层状态应该由：
  - `IngestRun`
  - 层级 revision
  - `CURRENT_*_REVISION`
  来表达。

## 3. 核心需求重述

结合你的要求，后续方案必须同时满足：

- 用户必须提供“裁判文书唯一 id”，否则不允许写入 Neo4j。
- 同一唯一文书 id 再次写入时，应被视为“更新同一文书”，而不是创建新文书。
- 初始解析、增量解析、检索层、发现层都可能单独更新。
- 下游层都依赖上游层的实体 / 关系 id，更新时不能把下游依赖打断。
- `retrieval` 可在不做向量化的情况下写入 Neo4j，但界面必须明确提醒“当前仅完成图结构写入，未完成向量准备”。
- `discovery` 必须先有可复现的持久化来源，才能作为正式层参与 diff / resync / update。

## 4. 总体方案

### 4.1 文书唯一身份

引入两个明确概念：

- `document_uid`
  - 用户输入的“裁判文书唯一 id”
  - 例如：`1780383896`
  - 是业务层唯一身份
- `doc_id`
  - Neo4j 内使用的图文档 id
  - 规则：`CASE:{document_uid}` 或 `GUIDE:{document_uid}`

强约束：

- 后续所有 Neo4j 写入都必须基于 `document_uid`。
- `row_id` 只能作为工作台会话 / 本地保存记录 id，不能再充当业务唯一文书 id。
- 如果用户没有填写 `document_uid`，前端点击任意 Neo4j 写入按钮时必须弹窗阻断。

### 4.2 四层写入的统一抽象

从存储模型看，建议统一为“文书 + 分层 revision”的结构：

- 文书层：
  - `Document`
- 解析层：
  - `BaseRevision`
  - 初始解析和增量解析都属于 `base`，只是 `parse_stage` 不同
- 检索层：
  - `RetrievalRevision`
- 发现层：
  - `DiscoveryRevision`

建议不把“初始解析”和“增量解析”拆成两个平级 graph layer，而是都归到 `base`：

- `graph_layer = base`
- `parse_stage = initial | incremental`
- `parse_revision_id` 区分每次解析版本

这样可以避免层级膨胀，同时保持语义清晰：

- `base` 是文书解析事实层
- `retrieval` 是基于某个 `base revision` 派生出的检索资产层
- `discovery` 是基于某个 `base revision` 或 `retrieval revision` 派生出的发现层

### 4.3 当前层 vs 历史层

后续每层都应同时支持两种状态：

- 当前生效快照
- 历史 revision

推荐模型：

- `Document -[:CURRENT_BASE_REVISION]-> BaseRevision`
- `Document -[:CURRENT_RETRIEVAL_REVISION]-> RetrievalRevision`
- `Document -[:CURRENT_DISCOVERY_REVISION]-> DiscoveryRevision`

历史 revision 不删除，只是当前指针切换。

这样可以同时解决：

- 同层多次更新
- 历史追溯
- 下游依赖回放
- “为什么这次 diff 和上次不一样”的审计问题

## 5. ID 设计原则

### 5.1 base 实体 id

`base` 层继续使用当前已经逐步收敛出来的 canonical 策略：

- `CourtCase`、`TrialOrganization`、`Judge` 使用稳定实体 id
- `Evidence`、`JudgmentResult`、`LegalProvisionElement` 继续在解析阶段做 canonical 压缩
- 所有关系端点都必须指向 canonical 实体 id

这部分的目标是：

- 同一文书重新解析后，只要语义实体没变，实体 id 尽量不变
- 下游层引用的 base 锚点不因“同文书重写”整体漂移

### 5.2 retrieval 实体 id

`retrieval` 层必须拆成两类 id：

- `retrieval_revision_id`
  - 代表一次检索资产生成 / 写入批次
- `retrieval_entry_id`
  - 代表一条检索资产

建议规则：

- `retrieval_revision_id = retrieval_rev:{doc_id}:{source_base_revision_id}:{bundle_hash}`
- `retrieval_entry_id = retrieval_entry:{retrieval_revision_id}:{entry_signature}`

注意：

- 当前 `RetrievalGraphNode` 是 entry 内部子图节点，不应假设跨 revision 稳定。
- 但它必须通过 `source_refs.entity_ids / stable_ids` 显式指向上游 canonical base 实体。

### 5.3 discovery 实体 id

`discovery` 层也必须拆成两类：

- `discovery_revision_id`
  - 代表一次 discovery history 写入批次
- `discovery_record_id`
  - 代表 history 里的某一步记录

建议规则：

- `discovery_revision_id = discovery_rev:{doc_id}:{source_base_revision_id}:{history_hash}`
- `discovery_record_id = discovery_record:{doc_id}:{record_id}`

`DiscoveryNode`、`DiscoveryAnchor` 必须带 `doc_id` 前缀，避免不同文书互相覆盖。

## 6. 分层更新策略

### 6.1 base 单独更新

当用户对同一文书再次做初始解析或增量解析时：

1. 根据 `document_uid` 找到 `Document`
2. 创建新的 `BaseRevision`
3. 重新写入当前版 `base` 实体和关系
4. 将 `Document -> CURRENT_BASE_REVISION` 指向新 revision
5. 旧 revision 保留为历史，不直接删除

同时进行依赖检查：

- 若 `retrieval` / `discovery` 依赖的 `source_base_revision_id` 不是当前 revision
- 则标记它们为：
  - `upstream_status = stale`
  - `requires_rebuild = true`

### 6.2 retrieval 单独更新

当用户只更新 `retrieval` 层时：

1. 不改 `base`
2. 生成新的 `RetrievalRevision`
3. 所有 `RetrievalEntry`、`RetrievalGraphNode` 都挂到该 revision
4. `Document -> CURRENT_RETRIEVAL_REVISION` 指向新 revision

关键要求：

- `RetrievalEntry` 必须保留来源：
  - `source_base_revision_id`
  - `source_parse_version_id`
  - `source_entity_ids`
- retrieval 不能自己发明新的 base 实体 id
- retrieval 只能引用当前或历史 `base` canonical 实体

### 6.3 discovery 单独更新

当用户只更新 `discovery` 层时：

1. discovery 必须先有持久化后的 `discovery_history`
2. 生成新的 `DiscoveryRevision`
3. 将本次 history 中全部记录写入该 revision
4. `Document -> CURRENT_DISCOVERY_REVISION` 指向新 revision

关键要求：

- discovery 必须显式记录：
  - `source_base_revision_id`
  - 可选 `source_retrieval_revision_id`
  - `history_hash`
- `DiscoveryAnchor` 必须优先锚到 canonical base 实体 id
- 只有锚不到正式 base 实体时，才允许退化为文本锚点

### 6.4 同层更新时如何“只更新这一层”

原则：

- 更新某一层时，只切换该层的 `CURRENT_*_REVISION`
- 不直接删除其他层当前 revision
- 不覆盖其他层的实体或关系

这样可以保证：

- `base` 更新不会直接抹掉 `retrieval` / `discovery`
- `retrieval` 更新不会动 `base`
- `discovery` 更新不会动 `base` / `retrieval`

## 7. 下游依赖如何不被破坏

这是本方案的核心。

### 7.1 不允许下游依赖“局部运行时 id”

后续必须禁止下游层依赖：

- 前端临时节点 id
- retrieval 内部 `chain_nodes` 的局部顺序号
- discovery 里纯文本占位字符串

允许依赖的只能是：

- canonical base 实体 id
- canonical base 关系 id
- 明确声明的上游 revision id

### 7.2 依赖断裂判断规则

当上游层更新后，下游层分三种情况：

1. 上游 canonical id 仍存在
   - 下游可继续引用
   - 标记为 `dependency_status = valid`

2. 上游 canonical id 不存在，但能通过对齐规则匹配到新的 canonical id
   - 允许自动重映射
   - 标记为 `dependency_status = remapped`
   - 必须生成 remap 记录

3. 上游 canonical id 已不存在，且无法重映射
   - 标记为 `dependency_status = broken`
   - 不自动篡改下游内容
   - 提醒用户重新构建 retrieval / discovery

### 7.3 哪些实体适合自动 remap

建议只对这几类允许自动 remap：

- `Evidence`
- `JudgmentResult`
- `LegalProvisionElement`
- `LegalProvision`
- `LegalSubject`

原因：

- 这些实体已有较稳定的 canonical / stable id 规则

不建议自动 remap 的：

- `RetrievalGraphNode`
- `DiscoveryNode`
- discovery 纯文本新节点

原因：

- 这些节点本来就是派生层产物，不是 base canonical 实体

## 8. retrieval 的产品与写入策略

### 8.1 向量化不应再作为硬阻塞

后续 retrieval 写入前校验要拆成两类：

- **硬阻塞**
  - 图链无效
  - `retrieval_text` 为空
  - 缺少 `document_uid`
  - 关键来源实体 id 缺失

- **软提醒**
  - 向量状态 `pending`
  - 向量状态 `stale`
  - 向量状态 `failed`

产品语义应调整为：

- 没做向量化也可以写 Neo4j `retrieval`
- 但前端必须明确提示：
  - 当前仅完成图层写入
  - 向量相关能力未就绪
  - 后续如需向量检索，仍需执行重新向量化

### 8.2 retrieval 链路修正策略

“修正链路”必须作为重点设计，而不是简单放行。

建议将 retrieval 条目状态分成：

- `graph_ready`
- `graph_invalid`
- `vector_pending`
- `vector_ready`
- `written_partial`
- `written_full`

推荐写入策略：

- 严格模式：
  - 有任意 `graph_invalid` 条目，则整体不写
- 兼容模式：
  - 只写 `graph_ready` 的条目
  - 跳过 `graph_invalid` 条目
  - 生成 `write_manifest.skipped_entries`

推荐默认：

- 对正式生产环境，优先用兼容模式
- 但界面要强提醒“共跳过 N 条链路异常资产”

这样可以避免：

- 因个别坏链路阻塞整批检索资产入库
- 又保留人工修正入口

## 9. discovery 的产品与写入策略

### 9.1 discovery 必须先持久化再写入

后续 discovery 层正式化后，写入前必须满足：

- 当前 `discovery_history` 已保存到后端记录

不建议继续允许“仅浏览器 `localStorage` 中存在，但直接写 Neo4j”的模式。

原因：

- 这样会造成：
  - Neo4j 有 discovery
  - 本地保存记录没有 discovery_history
  - `diff` / `resync` / 回放都失真

推荐流程：

1. 用户生成 discovery
2. 用户保存案例
3. 后端确认 `discovery_history` 已持久化
4. 才允许写 discovery 层

### 9.2 discovery 偏少时如何解释

后续界面需要明确区分：

- `record_count`
  - discovery history 有几条记录
- `new_node_count`
  - 所有记录累计生成了多少新节点
- `new_edge_count`
  - 所有记录累计生成了多少新边
- `anchor_count`
  - 其中有多少是锚点

这样用户不会把：

- “记录条数少”
- “新节点少”
- “锚点多”

混成一个“感觉偏少”。

## 10. 前端交互调整

### 10.1 必填唯一文书 id

在 `Workspace` 中增加一个明确输入区：

- 字段名：`文书唯一ID`
- 示例：`1780383896`
- 说明文案：
  - 这是裁判文书的业务唯一 id
  - Neo4j 中会转换成 `CASE:{document_uid}`

点击以下任意按钮前都必须校验：

- `写入 Neo4j`
- `写入检索层`
- `写入发现层`

若未填写：

- 弹窗提醒
- 阻止写入

### 10.2 写入前提示文案

建议提示拆分为：

- base：
  - 当前将更新同一文书的基础解析层
- retrieval：
  - 当前允许在未完成向量化的情况下写入图结构
  - 若存在链路异常条目，将跳过或阻止，取决于模式
- discovery：
  - 当前将基于已保存的 discovery history 写入
  - 若 history 未保存，则禁止写入

### 10.3 更新模式提示

当该 `document_uid` 已存在时，前端应显示：

- 本次将更新已有文书，而不是创建新文书
- 当前将影响的层：
  - `base`
  - `retrieval`
  - `discovery`
- 下游依赖状态：
  - `retrieval stale`
  - `discovery stale`

## 11. 后端接口调整建议

### 11.1 写入接口统一增加字段

建议三个写入接口统一增加：

- `document_uid`
- `doc_id`
- `source_base_revision_id`
- `write_mode`
  - `strict`
  - `compatible`

其中：

- `doc_id` 可由后端根据 `document_uid` 计算
- 但请求里仍允许显式传入，便于幂等验证

### 11.2 返回结构统一增加

建议返回统一增加：

- `created_new_document`
- `updated_existing_document`
- `created_revision_id`
- `previous_revision_id`
- `dependency_status`
- `skipped_entries`
- `stale_downstream_layers`

## 12. 稳健性分析

### 12.1 为什么该方案稳健

- 文书身份稳定：
  - `document_uid` 与 `row_id` 分离后，不会再把“本地会话 id”误当业务主键
- 层级边界清晰：
  - 每层只更新自己的 revision
- 下游依赖可追踪：
  - 每层显式记录依赖的上游 revision
- 历史可审计：
  - 多次写入保留历史 revision，而不是覆盖黑盒
- 可渐进落地：
  - 不必一步到位重写全部 schema，可先补前端唯一 id、写入校验、revision 元数据，再逐步引入完整 revision 节点

### 12.2 主要风险

- base canonical 规则仍需继续稳定
  - 否则上游 revision 更新后，下游 remap 成本高
- retrieval 当前有较多链路异常条目
  - 如果不做“跳过 + manifest”，会持续阻塞使用
- discovery 当前存在“会话态写入大于持久化记录”的问题
  - 若不强制先保存，后续 diff / resync 仍会漂移

### 12.3 推荐的稳健性底线

在真正开始实现更新体系前，至少先做到：

1. `document_uid` 前端必填
2. base / retrieval / discovery 写入都基于同一个 `doc_id`
3. retrieval 向量状态降为软提醒
4. discovery 必须先保存后写入
5. 每层写入结果都返回 `source_*_revision_id`

## 13. 推荐实施顺序

### 阶段 A：先补正确入口

- 前端增加 `document_uid` 输入与必填校验
- 所有 Neo4j 写入按钮统一走该业务唯一 id

### 阶段 B：补 retrieval 产品语义

- 向量状态从硬阻塞改为软提醒
- 链路问题保持硬阻塞或按兼容模式跳过
- 增加写入 manifest 的 `skipped_entries`

### 阶段 C：补 discovery 正式化

- discovery 必须先保存后写入
- `Workspace` discovery 写入只接受持久化 history
- `Database diff` 基于持久化 history 对账

### 阶段 D：补 revision 模型

- base / retrieval / discovery 全部引入 revision
- current 指针和历史 revision 分离

### 阶段 E：补依赖状态机

- 上游更新后，自动标记下游 `stale / valid / broken / remapped`

## 14. 本文对应的当前结论

- `retrieval` 现在之所以报 `40` 项阻塞，并不代表有 `40` 项必须修链。
- 当前阻塞混合了：
  - `20` 项未向量化
  - `10` 项链路无效
  - `10` 项正文为空
- `discovery` 当前已经能写入，但“已写入 Neo4j”不等于“已形成可复现的持久化来源”。
- `base` 当前在同一个 `doc_id` 下没有确认到活跃重复实体。
- 但如果继续不引入用户可控的唯一文书 id，后续出现“同文书多 doc_id 并存”的概率很高。

因此，后续最优先应先做：

- 前端唯一文书 id
- retrieval 非向量化可写但提醒
- discovery 保存后再写
- 分层 revision 设计

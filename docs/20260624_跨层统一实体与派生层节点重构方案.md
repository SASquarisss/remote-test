# 20260624_跨层统一实体与派生层节点重构方案

## 1. 背景与问题

当前 Neo4j 建模已经把 `base`、`retrieval`、`discovery` 三层都写进了图库，但 `retrieval` 与 `discovery` 仍然主要采用“复制节点”的方式建模：

- `base` 层写入正式本体实体，例如：
  - `Fact`
  - `DisputeFocus`
  - `Evidence`
  - `JudgmentResult`
  - `LegalProvision`
- `retrieval` 层将链路节点统一写成：
  - `RetrievalEntry`
  - `RetrievalGraphNode`
- `discovery` 层将发现节点统一写成：
  - `DiscoveryRecord`
  - `DiscoveryNode`
  - `DiscoveryAnchor`

这带来一个核心问题：

- 同一个语义实体在 `base` 中已经有一个正式节点
- 但到了 `retrieval` / `discovery`，又会被复制成新的派生层节点
- 最终图库里出现的是“平行副本”，而不是“统一实体图”

例如：

- `base` 中有一个 `(:DisputeFocus {id: "focus_xxx"})`
- `retrieval` 中又有一个 `(:RetrievalGraphNode {original_node_id: "focus_xxx", node_type: "DisputeFocus"})`

这两个节点虽然在语义上都指向“同一个争点”，但在图数据库里并不是同一个节点。

## 2. 当前实现的真实含义

### 2.1 node label 和 node_type 的区别

当前 `retrieval` / `discovery` 代码中存在两种“类型信息”：

- `label`
  - 这是 Neo4j 的正式标签
  - 例如：`RetrievalGraphNode`、`DiscoveryNode`
- `node_type`
  - 这是节点的普通属性
  - 例如：`DisputeFocus`、`Fact`、`JudgmentResult`

两者不是一回事。

例如当前 `retrieval` 的写入逻辑在 [neo4j_models.py](file:///home/sxc/wendao/remote-test/backend/neo4j_models.py#L307-L332)：

```python
node_props = {
    "id": graph_node_id,
    "doc_id": doc_id,
    "graph_layer": "retrieval",
    "source_collection": "retrieval_graph_nodes",
    "source_run_id": source_run_id,
    "bundle_id": str(bundle.get("bundle_id") or ""),
    "entry_id": entry_id,
    "original_node_id": original_id,
    "node_type": str(node.get("type") or ""),
    "label_text": str(node.get("label") or ""),
}
entity_payloads.append({
    "label": "RetrievalGraphNode",
    "id": graph_node_id,
    "properties": node_props,
})
```

这表示：

- 这个节点在 Neo4j 中的正式 label 是 `RetrievalGraphNode`
- 它只是通过属性 `node_type = "DisputeFocus"` 来说明“它看起来像一个争点”

因此：

- `node_type = DisputeFocus` 不等于该节点真的就是 `:DisputeFocus`
- 这也是为什么你在图库里会看到“重复语义节点”

### 2.2 Neo4j 是否支持一个节点有多个 label

支持。

例如一个节点完全可以同时拥有：

- `:RetrievalGraphNode`
- `:DisputeFocus`

但要注意：

- “同一个节点有多个 label”并不自动意味着“它就是 `base` 里那一个节点”
- 如果它的 `id` 不同，它仍然是另一个节点，只是多打了一个 label

所以这里真正的问题不是“能不能多 label”，而是：

- `retrieval` / `discovery` 是否应该继续创建新的节点身份
- 还是应该直接复用 `base` 的 canonical 节点身份

## 3. 目标原则

如果项目以本体实体为核心，那么后续应遵守以下原则：

### 3.1 统一实体原则

- 已经在 `base` 中存在的 canonical 本体实体，`retrieval` / `discovery` 层应优先复用同一节点
- 不再默认复制出新的 `RetrievalGraphNode` / `DiscoveryNode`

### 3.2 派生对象独立原则

- `retrieval` / `discovery` 中确实存在一些不是 base 本体实体的对象
- 这些对象仍然应该保留独立节点

例如：

- `RetrievalEntry`
- `DiscoveryRecord`
- discovery 里真正新增、尚未纳入本体的“推断节点”

### 3.3 层级通过关系表达，不通过复制节点表达

后续“一个实体属于哪一层”不应主要靠：

- 节点复制
- 节点上的 `graph_layer` 属性

而应主要靠：

- 某层 revision 节点
- 某层 entry / record 节点
- 层级关系

来表达。

## 4. 建议的新建模方式

### 4.1 实体层

图库中只保留一套 canonical 实体节点：

- `CourtCase`
- `TrialOrganization`
- `Judge`
- `LegalSubject`
- `Attorney`
- `Fact`
- `DisputeFocus`
- `LitigationClaim`
- `ProceduralOpinion`
- `ArgumentPoint`
- `JudicialAssessment`
- `Evidence`
- `JudgmentResult`
- `LegalProvision`
- `LegalProvisionElement`

这些节点在三层中共用一份身份。

### 4.2 派生层对象

派生层只保留真正属于派生层的对象：

- `RetrievalRevision`
- `RetrievalEntry`
- `DiscoveryRevision`
- `DiscoveryRecord`
- `DiscoveryDerivedNode`
- `DiscoveryTextAnchor`

这里有两个重要调整：

- 原 `RetrievalGraphNode` 不再作为默认节点类型存在
- 原 `DiscoveryNode` 仅保留为“真正新增且无法对齐到 base canonical 实体”的派生节点，建议更名为 `DiscoveryDerivedNode`

### 4.3 关系模型

建议新增 / 重构以下关系：

- `Document -[:CURRENT_BASE_REVISION]-> BaseRevision`
- `Document -[:CURRENT_RETRIEVAL_REVISION]-> RetrievalRevision`
- `Document -[:CURRENT_DISCOVERY_REVISION]-> DiscoveryRevision`

- `RetrievalRevision -[:HAS_ENTRY]-> RetrievalEntry`
- `RetrievalEntry -[:USES_ENTITY]-> BaseEntity`
- `RetrievalEntry -[:USES_RELATION]-> BaseRelationReference`
- `RetrievalEntry -[:NEXT_IN_CHAIN]-> RetrievalEntryEntityRef` 或使用顺序属性表达链路顺序

- `DiscoveryRevision -[:HAS_RECORD]-> DiscoveryRecord`
- `DiscoveryRecord -[:REFERS_TO_ENTITY]-> BaseEntity`
- `DiscoveryRecord -[:PROPOSES_RELATION]-> BaseEntity / DiscoveryDerivedNode`
- `DiscoveryRecord -[:PRODUCES_DERIVED_NODE]-> DiscoveryDerivedNode`
- `DiscoveryRecord -[:USES_TEXT_ANCHOR]-> DiscoveryTextAnchor`

## 5. retrieval 重构方案

### 5.1 当前 retrieval 的问题

当前 `retrieval` 把 `chain_nodes` 全部写成 `RetrievalGraphNode`，存在三个问题：

- base 已有实体被重复复制
- `node_type` 只是字符串属性，不能参加正式 label / 约束体系
- entry 内部链路只在 retrieval 副本节点之间成立，无法天然复用 base 图上的实体关系

### 5.2 建议改造

对于 `chain_nodes` 中的每个节点，改成三段判定：

#### 第一类：可映射到 base canonical 实体

判定依据：

- `original_node_id` 能直接映射到 base canonical id
- 或 `source_refs.entity_ids / stable_ids` 能回指到 base 实体

处理方式：

- 不创建 `RetrievalGraphNode`
- 直接复用对应 base 节点
- 建立：
  - `RetrievalEntry -[:USES_ENTITY {role, seq}]-> (:DisputeFocus)`
  - `RetrievalEntry -[:USES_ENTITY {role, seq}]-> (:Fact)`

#### 第二类：无法映射到 base，但属于结构化派生节点

例如：

- 某些为了 retrieval 组织链路而生成的中间节点
- 确实不在 base 本体中

处理方式：

- 创建独立派生节点
- 建议 label 改为：
  - `RetrievalDerivedNode`
- 并显式标记：
  - `derived_from_entry_id`
  - `node_type`
  - `origin = retrieval`

#### 第三类：纯展示节点

例如：

- 只为拼链路文字而临时生成的汇总节点

处理方式：

- 不应入图
- 只保留在 `payload_json` 或前端渲染态

### 5.3 retrieval 链路表达方式

后续 retrieval 链路不应再用：

- `RetrievalGraphNode -> RetrievalGraphNode`

改为：

- `RetrievalEntry -[:USES_ENTITY {seq: 1}]-> EntityA`
- `RetrievalEntry -[:USES_ENTITY {seq: 2}]-> EntityB`
- `RetrievalEntry -[:USES_ENTITY {seq: 3}]-> EntityC`

同时保存链路边定义：

- `RetrievalEntry.relation_path`
- 或单独保存：
  - `(:RetrievalEntry)-[:USES_RELATION {seq:1, relation_type:"proves_fact"}]->(:BaseRelationRef)`

推荐第一阶段先采用轻量做法：

- 顺序放在 `USES_ENTITY.seq`
- 边类型放在 `RetrievalEntry.payload_json.graph_payload.chain_edges`

这样既不丢结构，又不需要立刻把“关系本身也实体化”。

## 6. discovery 重构方案

### 6.1 当前 discovery 的问题

当前 `discovery` 写入分两类：

- `new_nodes` 写成 `DiscoveryNode`
- 指向原图的端点写成 `DiscoveryAnchor`

这意味着：

- discovery 无法真正复用已有 canonical 实体
- `DiscoveryAnchor` 更像“文本替身”而不是“实体引用”

### 6.2 建议改造

对 discovery `new_nodes / new_edges` 进行分流：

#### 第一类：可对齐到 base canonical 实体

例如：

- `new_nodes` 中的某个节点本质就是已有的 `DisputeFocus`
- `new_edges` 的端点能直接对齐到 `Fact`、`Evidence`、`LegalProvisionElement`

处理方式：

- 不新建 `DiscoveryNode`
- 直接建立：
  - `DiscoveryRecord -[:REFERS_TO_ENTITY]-> BaseEntity`
  - `DiscoveryRecord -[:PROPOSES_RELATION {relation_type:"supports_fact"}]-> BaseEntity`

#### 第二类：真正新增的推理节点

例如：

- discovery 新得出的中间判断
- 尚未进入本体注册表的新概念节点

处理方式：

- 写成独立派生节点
- 建议 label 从 `DiscoveryNode` 调整为：
  - `DiscoveryDerivedNode`

#### 第三类：仅文本锚点

只有当端点既不是已有 base 实体，也不是明确的 discovery 新节点时，才降级为：

- `DiscoveryTextAnchor`

这类节点应被视为兜底对象，而不是默认对象。

## 7. 为什么不是简单给 RetrievalGraphNode 多打一个 DisputeFocus label

表面上看，好像可以把当前 retrieval 节点改成：

- `:RetrievalGraphNode:DisputeFocus`

但这不是最终解法，原因有 4 个：

### 7.1 它仍然可能是另一个节点

如果 `id` 还是：

- `retrieval_node:{entry_id}:{original_id}`

那它只是“一个带 `DisputeFocus` label 的 retrieval 副本节点”，仍然不是 base 中那个 `focus_xxx`

### 7.2 它会让约束空间混乱

当前 `DisputeFocus.id` 是唯一约束。

如果 retrieval 副本节点也打上 `:DisputeFocus`，但 `id` 又不是 canonical `focus_xxx`，则：

- 要么冲突
- 要么强行换 id

这都不理想。

### 7.3 它会让查询歧义变大

以后查询：

```cypher
MATCH (n:DisputeFocus)
```

你拿到的是：

- canonical base 节点
- 还是 retrieval 副本节点

这会让图库语义变混。

### 7.4 它没有解决“同一实体身份”的本质问题

多 label 只是在“分类”层面补充信息。

你想要的是“身份统一”。

身份统一只能靠：

- 复用同一 canonical `id`
- 不再创建重复节点

## 8. 迁移策略

这次重构不建议一步到位替换，应采用分阶段迁移。

### 阶段 1：先引入“实体引用优先”策略

目标：

- `retrieval` / `discovery` 先学会优先复用 base canonical 实体

做法：

- 在 `build_retrieval_layer_payload()` 中新增映射：
  - `original_node_id -> base label + canonical id`
- 在 `build_discovery_layer_payload()` 中新增映射：
  - `node_ref -> base label + canonical id`

规则：

- 能对齐到 base 的，就不再建副本节点
- 对齐不到的才建派生节点

### 阶段 2：保留旧 schema，但降级旧节点类型

目标：

- 避免大规模破坏当前查询与 diff

做法：

- `RetrievalGraphNode` 不立即删除
- 但只作为兜底派生节点使用
- `DiscoveryNode` 只保留为真正新增节点
- `DiscoveryAnchor` 重命名为逻辑上的 `TextAnchor`，代码层可后续再统一调整

### 阶段 3：重写 retrieval / discovery diff 口径

当前 diff 统计主要看：

- `RetrievalGraphNode`
- `DiscoveryNode`
- `DiscoveryAnchor`

后续要改成同时统计：

- `entry / record` 数量
- 引用到的 canonical base 实体数
- 真正新增的派生节点数

也就是说，后续层内统计口径应拆成：

- `entity_ref_count`
- `derived_node_count`
- `record_count`

### 阶段 4：子图查询切换到“按关系取层”

当前很多查询依赖：

- 节点属性 `graph_layer`
- `HAS_ENTITY {graph_layer}`

后续要更多改成：

- 先找 `CURRENT_*_REVISION`
- 再沿层级关系找到本层引用的实体和派生节点

### 阶段 5：最后清理旧副本节点模型

等新查询、diff、前端都适配后，再逐步：

- 废弃 `RetrievalGraphNode` 的主路径使用
- 废弃 `DiscoveryAnchor` 的默认使用

## 9. 影响范围

### 9.1 后端

需要改动：

- `backend/neo4j_models.py`
- `backend/neo4j_service.py`
- `backend/neo4j_repository.py`
- `backend/app.py`
- `backend/neo4j_schema.py`

重点变更：

- `RetrievalGraphNode` 不再是默认节点类型
- `DiscoveryNode` / `DiscoveryAnchor` 改成“仅在无法复用 base 时使用”
- 增加实体引用关系写入

### 9.2 前端 Workspace

需要改动：

- `retrieval` / `discovery` 写入成功后的统计文案
- Neo4j 状态面板的实体数解释

因为后续：

- retrieval 写入成功不再等于“写入了 N 个 RetrievalGraphNode”
- 而是“写入了 N 条检索资产，引用了 M 个 canonical 实体，新增了 K 个派生节点”

### 9.3 Database

需要改动：

- `diff-case`
- `case-subgraph`
- 图层差异说明

因为后续：

- 同一个 `DisputeFocus` 节点既属于 base，又会被 retrieval / discovery 引用
- 因此不能再简单按“层内节点复制数”来比较

## 10. 稳健性分析

### 10.1 优势

- 更符合“以本体实体为核心”的原则
- 图数据库里真正只有一份 canonical 实体
- retrieval / discovery 与 base 不再各自维护一套副本节点
- 后续跨层查询、图推理、节点详情聚合都更自然

### 10.2 风险

- 查询逻辑需要明显调整
- 当前依赖 `graph_layer` 节点属性的地方要逐步迁移
- diff 统计口径会变化
- 部分旧数据需要迁移或重写

### 10.3 为什么值得做

因为如果不做，后面会越来越重：

- retrieval 会继续复制更多 base 实体
- discovery 也会继续造更多“看似像本体、其实不是本体”的节点
- 图会越来越像“多层快照集合”，而不是“统一知识图谱”

## 11. 明确建议

### 11.1 必须做的

- `retrieval` / `discovery` 优先复用 base canonical 实体
- 同一语义实体不再默认创建副本节点
- `node_type` 继续保留，但只作为辅助属性，不再承载“真实类型身份”

### 11.2 可以保留的

- `RetrievalEntry`
- `DiscoveryRecord`
- 真正的派生节点

### 11.3 应逐步废弃的

- “所有 retrieval 链路节点都写成 `RetrievalGraphNode`”
- “所有 discovery 新节点都写成 `DiscoveryNode`”
- “所有无法直连 base 的端点都先写成 `DiscoveryAnchor`”

## 12. 推荐实施顺序

1. `retrieval` 优先复用 canonical base 实体
2. `discovery` 优先复用 canonical base 实体
3. 将 `RetrievalGraphNode` 降级为兜底派生节点
4. 将 `DiscoveryNode` 明确区分为 `DiscoveryDerivedNode`
5. 重写 `Database diff / subgraph / status` 口径
6. 最后再清理旧的副本节点模型

## 13. 一句话结论

你要的并不是“给 `RetrievalGraphNode` 再补一个 `DisputeFocus` label”。

你真正要的是：

- `base` 中的 canonical 实体只保留一份
- `retrieval` / `discovery` 不再复制这份实体
- 它们通过关系引用同一个实体节点

这才是更稳、更符合本体中心设计的重构方向。

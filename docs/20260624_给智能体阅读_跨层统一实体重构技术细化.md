# 20260624_给智能体阅读_跨层统一实体重构技术细化

## 1. 文档定位

本文是给后续继续接手开发的智能体或工程实现者阅读的技术文档，目标是把“跨层统一实体重构”拆成可以直接落到代码和数据模型上的执行说明。

本文允许出现：

- 具体标签名
- 具体关系名
- 具体字段名
- 具体函数入口
- 具体迁移顺序

而这些内容不再放到“给你阅读”的业务文档中。

## 2. 重构目标的技术表达

重构后的总目标：

- `base` 中已有的 canonical 实体，在 `retrieval` / `discovery` 中优先复用同一节点身份
- `RetrievalGraphNode` 不再是默认节点类型
- `DiscoveryNode` 不再是默认节点类型
- `DiscoveryAnchor` 不再是默认端点表达，降级为兜底文本锚点

技术上需要完成两件事：

1. 写入 payload 生成逻辑改造
2. 查询 / diff / status 口径改造

## 3. 建议的新模型

### 3.1 canonical 实体层

保留并持续复用当前正式本体实体标签：

- `CourtCase`
- `TrialOrganization`
- `Judge`
- `LegalSubject`
- `Attorney`
- `Fact`
- `DisputeFocus`
- `LitigationClaim`
- `ProceduralOpinion`
- `ArgumentPoint`
- `JudicialAssessment`
- `Evidence`
- `JudgmentResult`
- `LegalProvision`
- `LegalProvisionElement`

要求：

- 以上实体继续使用 canonical id
- retrieval / discovery 不得在可映射时重新创造一份副本身份

### 3.2 分层对象

保留分层记录对象：

- `BaseRevision`
- `RetrievalRevision`
- `RetrievalEntry`
- `DiscoveryRevision`
- `DiscoveryRecord`
- `DiscoveryDerivedNode`
- `DiscoveryTextAnchor`
- 过渡阶段允许保留 `RetrievalGraphNode`

其中：

- `RetrievalGraphNode` 在阶段 1 和阶段 2 仅作为兜底派生节点使用
- 后续可视需要重命名为 `RetrievalDerivedNode`

### 3.3 关系建议

建议逐步引入或强化以下关系：

- `Document -[:CURRENT_BASE_REVISION]-> BaseRevision`
- `Document -[:CURRENT_RETRIEVAL_REVISION]-> RetrievalRevision`
- `Document -[:CURRENT_DISCOVERY_REVISION]-> DiscoveryRevision`
- `RetrievalRevision -[:HAS_ENTRY]-> RetrievalEntry`
- `RetrievalEntry -[:USES_ENTITY]-> BaseEntity`
- `DiscoveryRevision -[:HAS_RECORD]-> DiscoveryRecord`
- `DiscoveryRecord -[:REFERS_TO_ENTITY]-> BaseEntity`
- `DiscoveryRecord -[:PRODUCES_DERIVED_NODE]-> DiscoveryDerivedNode`
- `DiscoveryRecord -[:USES_TEXT_ANCHOR]-> DiscoveryTextAnchor`

阶段 1 不强制把所有关系实体化，允许把链路边定义继续留在 `payload_json`。

## 4. 代码层主改动点

### 4.1 `backend/neo4j_models.py`

这是本次重构的第一核心文件。

需要重点改造的方向：

- `build_retrieval_layer_payload()`
- `build_discovery_layer_payload()`

#### retrieval 目标逻辑

对每个 `chain_node` 做三段分流：

1. 可映射到 base canonical 实体
2. 无法映射但属于结构化派生节点
3. 纯展示节点

处理规则：

- 第 1 类：
  - 不创建 `RetrievalGraphNode`
  - 生成 `RetrievalEntry -> BaseEntity` 的引用关系 payload
- 第 2 类：
  - 创建兜底派生节点
  - 继续使用 `RetrievalGraphNode` 或切换为 `RetrievalDerivedNode`
- 第 3 类：
  - 不入图
  - 仅保留在 payload 原文或前端态

建议在 retrieval payload 生成阶段引入辅助映射函数，例如：

- `resolve_base_entity_ref(node, base_entity_index)`
- `build_retrieval_entity_refs(...)`
- `build_retrieval_fallback_nodes(...)`

#### discovery 目标逻辑

对 `new_nodes`、`new_edges` 的端点做分流：

1. 能直接对齐到 base canonical 实体
2. 属于真正新增推理节点
3. 只能退化为文本锚点

处理规则：

- 第 1 类：
  - 不创建 `DiscoveryNode`
  - 写成 `DiscoveryRecord -> BaseEntity` 引用
- 第 2 类：
  - 创建 `DiscoveryDerivedNode`
- 第 3 类：
  - 创建 `DiscoveryTextAnchor`

建议引入辅助函数，例如：

- `resolve_discovery_entity_ref(node_ref, base_entity_index)`
- `build_discovery_record_entity_refs(...)`
- `build_discovery_derived_nodes(...)`
- `build_discovery_text_anchors(...)`

### 4.2 `backend/neo4j_repository.py`

这是第二核心文件。

当前问题：

- 当前节点 upsert 以单 label `MERGE (n:{label} {id: $id})` 为主
- 查询层大量依赖 `graph_layer` 和 `HAS_ENTITY {graph_layer}`

改造方向：

- 继续支持旧写法，保证过渡期兼容
- 新增面向“引用关系”的 upsert 能力
- 子图查询逐步从“按节点层属性取层”迁移到“按 revision 和引用关系取层”

建议增加的 repository 能力：

- 写入 `RetrievalEntry -> BaseEntity` 引用关系
- 写入 `DiscoveryRecord -> BaseEntity` 引用关系
- 写入 `DiscoveryRecord -> DiscoveryDerivedNode`
- 查询某 `doc_id` 当前 revision 下的 entry / record 引用子图

### 4.3 `backend/neo4j_service.py`

职责：

- 负责组织 revision、payload 构建、写入顺序、旧数据兼容

建议改造：

- `write_retrieval_layer` 中先构建 base 实体索引，再构建 retrieval 引用 payload
- `write_discovery_layer` 中先构建 base 实体索引，再构建 discovery 引用 payload
- 返回结果中增加：
  - `entity_ref_count`
  - `derived_node_count`
  - `fallback_anchor_count`

### 4.4 `backend/app.py`

需要同步调整的方向：

- `diff-case`
- `case-subgraph`
- 层统计
- 写入结果摘要

关键改造点：

- retrieval 层统计不再只看 `RetrievalGraphNode`
- discovery 层统计不再只看 `DiscoveryNode` / `DiscoveryAnchor`
- 改为同时返回：
  - `record_count`
  - `entity_ref_count`
  - `derived_node_count`
  - `text_anchor_count`

### 4.5 `backend/neo4j_schema.py`

需要处理的不是简单删约束，而是分阶段降级旧模型。

建议：

- 短期保留 `RetrievalGraphNode.id` 唯一约束
- 短期保留 `DiscoveryNode.id` 唯一约束
- 短期保留 `DiscoveryAnchor.id` 唯一约束
- 新增 `DiscoveryDerivedNode.id`、`DiscoveryTextAnchor.id` 约束时，注意迁移时机

原则：

- 先兼容写入路径
- 再迁移查询路径
- 最后处理 schema 清理

## 5. 映射策略

### 5.1 retrieval 对齐 base 的主依据

建议优先级：

1. `original_node_id`
2. `source_refs.entity_ids`
3. `source_refs.stable_ids`
4. 必要时按 `node_type + 规范化文本` 做兜底匹配

要求：

- 只有在匹配结果唯一且可信时，才复用 base canonical 实体
- 匹配不唯一时，降级到兜底派生节点，不要强行误绑

### 5.2 discovery 对齐 base 的主依据

建议优先级：

1. `node_ref.entity_id`
2. `node_ref.stable_id`
3. `source_refs.entity_ids`
4. 必要时按 `type + text + provenance` 兜底匹配

要求：

- 对齐到 base 后，`DiscoveryRecord` 直接引用 base 实体
- 无法可靠对齐时，不要隐式映射到错误实体

## 6. 迁移阶段的兼容策略

### 6.1 阶段 1

目标：

- 引入“实体引用优先”
- 保持旧 schema 和旧查询尽量可运行

做法：

- retrieval / discovery payload 先支持 `entity_ref`
- 只把确实无法映射的对象继续写成旧节点模型

### 6.2 阶段 2

目标：

- 改造 `diff`、`status`、`subgraph`

做法：

- 前后端统计项改成引用数、派生节点数、记录数
- 逐步减少对 `graph_layer` 节点属性的依赖

### 6.3 阶段 3

目标：

- 清理旧主路径

做法：

- `RetrievalGraphNode` 不再作为默认写入标签
- `DiscoveryNode` 全量迁移到 `DiscoveryDerivedNode`
- `DiscoveryAnchor` 逻辑上改为 `DiscoveryTextAnchor`

## 7. 前端需要跟随的变化

### 7.1 Workspace

写入成功提示建议从“写入多少个层内节点”改成：

- 写入了多少条 retrieval / discovery 记录
- 引用了多少个 canonical 实体
- 新增了多少个派生节点
- 生成了多少个文本锚点

### 7.2 Database

需要跟随后端口径变更：

- diff 面板
- status 面板
- case subgraph 展示逻辑

重点：

- 同一个实体可能被 base、retrieval、discovery 同时引用
- 不能再简单用“某层复制了多少个节点”解释差异

## 8. 数据迁移建议

不建议对旧库做一次性复杂迁移脚本后再切换。

更稳妥的路线：

1. 先完成新写入逻辑
2. 新数据按新模型写入
3. 查询逻辑兼容旧数据和新数据
4. 观察稳定后，再决定是否对旧数据做离线迁移或直接重写

原因：

- 当前仍在联调期
- schema、统计口径、revision 体系都还在演进
- 过早做重迁移容易反复返工

## 9. 风险点

主要风险：

- base canonical 实体对齐仍可能出现误匹配
- retrieval / discovery 当前 payload 的来源字段未必足够稳定
- 旧查询路径大量依赖 `graph_layer`
- 统计口径变化后，前端文案需要一起改

防守策略：

- 宁可降级为派生节点，也不要误绑定 canonical 实体
- 过渡期保留旧标签和旧约束
- 每阶段都保留可观测统计结果

## 10. 推荐的直接开发顺序

1. 改 `backend/neo4j_models.py`，让 retrieval 优先引用 base 实体
2. 改 `backend/neo4j_models.py`，让 discovery 优先引用 base 实体
3. 改 `backend/neo4j_service.py` 返回新统计项
4. 改 `backend/app.py` 的 diff / subgraph / status 口径
5. 改 `backend/neo4j_repository.py` 的查询与引用关系写入
6. 最后再评估 schema 清理和旧数据迁移

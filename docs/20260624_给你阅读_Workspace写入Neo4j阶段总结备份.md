# 20260624_给你阅读_Workspace写入Neo4j阶段总结备份

## 1. 本文用途

这份文档用于备份当前 `Workspace -> 写入 Neo4j` 这一阶段的整体结果。

阅读目标是：

- 你之后自己回看时，可以快速知道这轮到底做到了什么
- 后续如果换一个智能体继续接手，它也能先通过这份文档理解当前业务状态

这份文档偏重：

- 业务逻辑
- 用户体验变化
- 为什么这样调整
- 当前已经验证到什么程度

不把太细的函数、变量、接口细节全部展开，那部分会放到配套的“给智能体阅读”文档里。

## 2. 这轮工作的核心目标

这轮工作的目标，不是单纯“把数据写进 Neo4j”，而是把 `Workspace` 页触发的三层写入尽量做成：

- 能写
- 可解释
- 尽量不重复造节点
- 与本体结构更一致

具体覆盖了 3 层：

- `base`
- `retrieval`
- `discovery`

其中最重要的业务原则是：

- `base` 已经有正式实体的，后续层应尽量复用
- `retrieval` 和 `discovery` 不应默认再复制一套“同语义、不同身份”的节点

## 3. 当前已经完成的事情

### 3.1 base 层写入已经打通并完成一致性联调

当前 `Workspace` 的基础解析结果可以正式写入 Neo4j。

并且已经处理过一批关键一致性问题，包括：

- 显式关系写入
- 隐式关系 / `derived_relations` 写入
- 主图、本体、Neo4j 的节点边界逐步对齐

这意味着：

- `base` 现在已经不是“测试性质的写库”
- 而是当前这套 Neo4j 接入的稳定底座

### 3.2 retrieval 层已经从“默认复制节点”收口到“实体引用优先”

最开始的 retrieval 写入存在两个问题：

- 一部分向量状态被错误地当成硬阻塞，导致明明可以写却写不进去
- 写进去之后，很多本来在 `base` 里已有的实体，又被写成新的 `RetrievalGraphNode`

这轮已经做了两类修复：

第一类是写入前校验修复：

- 向量 `pending / stale / failed` 不再阻止写入
- 真正的链路错误和正文为空，仍然保留阻塞
- 并且已经改成“兼容模式”：
  - 有问题的 retrieval 资产可以跳过
  - 没问题的可以继续写入

第二类是建模修复：

- retrieval 现在会优先复用 `base` 的正式实体
- 只有无法可靠对齐时，才保留为兜底的 `RetrievalGraphNode`

这意味着：

- retrieval 已经不再是“无差别复制节点”
- 而是开始向“引用正式实体”收口

### 3.3 discovery 层也已经开始做“实体引用优先”

discovery 最开始的问题比 retrieval 更明显：

- `DiscoveryNode` 和 `DiscoveryAnchor` 被大量创建
- 一部分和 `base` 正式实体重复
- 发现记录之间还会彼此重复造同语义节点

这轮已经完成的收口包括：

- `ArgumentPoint / DisputeFocus / LitigationClaim` 等可直接复用 `base` 的对象，优先复用
- `SentencingCircumstance / EvidenceChain` 开始按“文书级稳定派生节点”思路收口
- `LegalProvisionElement` 不再一刀切处理，而是分成：
  - 能复用 `base` 的正式法条要件
  - 需要保留为个案适用表达的 `AppliedLegalProvisionElement`
- `ArgumentOutcome` 已经不再作为普通发现节点写入，而是降成关系属性

### 3.4 discovery 的统计口径已经改了

这次很重要的一点是：

discovery 不再继续用“节点数越多越好”来表达。

现在 Database 页面对 discovery 的理解已经改成：

- `实体引用数`
- `文书级派生节点数`
- `枚举锚点数`

这比原来只看：

- `DiscoveryNode`
- `DiscoveryAnchor`

更符合真实业务语义。

## 4. 现在用户在 Workspace 的体验是什么

### 4.1 base 层

用户在 `Workspace` 点击基础写入时：

- 会把正式解析结果写到 Neo4j
- 现在已经具备基本的一致性可核查能力

### 4.2 retrieval 层

用户在 `Workspace` 点击检索层写入时：

- 不再因为“尚未向量化”而整体被卡住
- 如果某些检索资产链路异常，会跳过异常项
- 其余正常资产继续写入

这比原来更符合真实使用场景，因为：

- 检索层并不一定总能先把所有 embedding 补齐
- 但 Neo4j 写入仍然是有价值的

### 4.3 discovery 层

用户在 `Workspace` 点击发现层写入时：

- 写入的是 discovery record 及其引用、派生结果
- 不再默认把所有 discovery 结果都写成新的普通节点
- 更接近“基于正式实体进行推理补充”的模型

## 5. 当前验证结论

这轮并不是只做代码修改，而是做过多轮真实验证。

已经确认过的结论包括：

### 5.1 retrieval 阻塞问题已被拆开

原来前端提示的 `40` 项阻塞，并不全是同类问题。

拆开后发现：

- 一部分只是 embedding 未就绪
- 一部分才是真正的链路错误或正文为空

现在已经把这两者区分开了。

### 5.2 retrieval 重复节点问题已明显收敛

已经实际写脚本检查过 retrieval 写入结果，确认：

- `Fact`
- `DisputeFocus`
- `LegalSubject`

这类本可复用 `base` 的对象，原来确实存在“明明已有实体，却仍新增 retrieval 节点”的问题。

后续已经针对这类情况补了复用规则，当前已经明显收敛。

### 5.3 discovery 重复问题已明显收敛

这轮对 discovery 做过真实重写验证，结果说明：

- 与 `base` 重复的一部分 discovery 节点已经收掉
- discovery 记录之间同语义的重复节点也已明显减少
- `ArgumentOutcome` 已经不再作为实体存在

### 5.4 discovery 的新口径已经能直接看

当前这份文书的 discovery 经过重写验证后，已经可以按新口径解释：

- 实体引用
- 文书级派生节点
- 枚举锚点

也就是说，现在 discovery 更像“推理层对正式实体的补充”，而不是“再复制一遍图”。

## 6. 当前最重要的业务结论

这轮开发结束后，已经可以把当前 Neo4j 接入理解成：

- `base` 负责正式实体和正式关系
- `retrieval` 负责说明某条检索资产引用了哪些正式实体
- `discovery` 负责说明某条发现记录基于哪些正式实体，提出了哪些个案推理节点和结论

这比最早的状态更接近你一开始反复强调的目标：

- 主图
- 本体
- Neo4j

三者应尽量统一，而不是长期各有一套平行表达。

## 7. 当前仍然存在的边界

虽然 Workspace 写入 Neo4j 这一阶段基本测试完了，但并不代表后续完全没有可继续优化的点。

目前仍然保留的边界主要有：

### 7.1 retrieval 仍有少量兜底节点

对一些无法稳定对齐到 `base` 的 retrieval 节点，当前仍保留兜底 `RetrievalGraphNode`。

这不是 bug，而是当前为了避免误绑做的保守处理。

### 7.2 discovery 仍保留部分派生节点

例如：

- `AppliedLegalProvisionElement`
- `SentencingCircumstance`
- `EvidenceChain`

这些不是简单的“重复节点”，而是 discovery 层本来就应保留的一部分推理产物。

### 7.3 一些页面提示文案仍可继续优化

例如：

- `Workspace` 的 discovery 写入成功提示目前仍主要展示 `record_count`

这不影响写入正确性，但后续如果要进一步提升可解释性，还可以继续优化文案。

## 8. 当前建议如何理解这一阶段是否完成

如果只看“Workspace 写入 Neo4j”这一阶段，可以认为已经进入：

- 功能可用
- 关键问题已收口
- 业务语义基本稳定
- 可作为后续阶段底座

换句话说，这一阶段现在更适合被理解为：

- “一轮核心功能收口完成”

而不是：

- “还只是早期试验接入”

## 9. 如果后续继续做，建议的自然延伸方向

如果后续继续往下推进，建议优先考虑下面几类工作：

1. 继续统一更新模型和 revision 模型
2. 继续完善文书唯一 `document_uid` 的完整流程
3. 继续优化 Database 页和 Workspace 页的文案与统计解释
4. 继续把 discovery 的关系语义表达做得更标准

但这些都属于下一阶段工作，不影响当前“Workspace 已基本完成 Neo4j 写入能力验证”的结论。

## 10. 本文结论

当前 `Workspace -> 写入 Neo4j` 这一阶段，已经完成了从“能写”到“基本可解释、可核查、可作为后续底座”的转变。

最关键的变化不是多写了多少数据，而是：

- `base` 更稳定
- `retrieval` 更少重复
- `discovery` 更符合推理层定位
- Database 的统计口径更接近真实业务语义

因此，这一阶段可以视为：

- 基本测试完成
- 可归档备份
- 可作为后续智能体继续接手的正式起点

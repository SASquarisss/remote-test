# 20260624_给智能体阅读_发现层派生节点收口规则表

## 1. 目标

本文件用于约束 discovery 层以下对象的落库策略：

- `LegalProvisionElement`
- `SentencingCircumstance`
- `EvidenceChain`
- `ArgumentOutcome`

目标不是统一“全部复用”或“全部派生”，而是按语义层次区分：

- `base canonical entity`
- `document-level canonical discovery derived node`
- `enum/property`

## 2. 总体规则

### 2.1 三层判定顺序

对 discovery 中的候选对象，按下面顺序判定：

1. 能否直接复用 `base`
2. 不能复用时，是否应收口成文书级 canonical discovery derived node
3. 如果既不适合复用，也不适合保留为稳定节点，则降级成关系属性或枚举值

### 2.2 不再接受的旧模式

以下模式不应继续作为默认行为：

- `new_nodes` 一律写成 `DiscoveryNode`
- `new_edges` 中所有外部端点一律写成 `DiscoveryAnchor`
- 不区分“正式本体实体”和“个案派生推理对象”

## 3. LegalProvisionElement

### 3.1 语义定位

- `base LegalProvisionElement`
  - 正式法条要件
  - 来源于解析后的结构化法条要件抽取
- `discovery LegalProvisionElement`
  - 可能是：
    - 对正式法条要件的重述
    - 本案中的解释性表达
    - 带数额阈值、个案限定的适用表达

### 3.2 判定结果

- 强匹配到 `base` 时：复用 `base LegalProvisionElement`
- 无法强匹配，但明显属于“个案解释后的要件表达”时：保留为 `AppliedLegalProvisionElement`

### 3.3 推荐标签

- 直接复用时：
  - `:LegalProvisionElement`
- 保留派生时：
  - `:DiscoveryNode`
  - `node_type = AppliedLegalProvisionElement`

如果后续愿意进一步清晰化，也可正式升级成独立标签：

- `:AppliedLegalProvisionElement`

### 3.4 复用判定字段

第一档：直接 id 命中

- `original_node_id`

第二档：文本强匹配

- `label`
- `content`
- 归一化后与 `base LegalProvisionElement.content / preview_text` 唯一命中

第三档：法条上下文辅助匹配

- 同时参考关联边端点：
  - 指向的 `LegalProvision`
  - 指向的 `Fact`
  - 指向的 `JudicialAssessment`

### 3.5 判定为“保留派生”的信号

存在以下任一情况时，不建议直接复用 `base`：

- 含案件数额阈值
- 含裁判解释性前缀
- 含“本案中”“本案体现”“认定为”等个案解释语气
- 同一文本无法唯一命中 `base`

### 3.6 provenance 字段

无论复用还是派生，都保留：

- `record_id`
- `source_run_id`
- `original_node_id`
- `payload_json`
- `matched_base_entity_id` 或 `resolved_entity_id`

## 4. SentencingCircumstance

### 4.1 语义定位

这是典型 discovery 派生对象：

- 不适合回写到 `base`
- 但需要在文书内保持稳定身份

### 4.2 模型结论

建议收口为：

- 文书级 canonical discovery derived node

推荐独立标签：

- `:DiscoveryDerivedNode`
  - `derived_type = SentencingCircumstance`

如果暂时不引入新标签，也至少应保证：

- `DiscoveryNode.id` 不再按 `record_id + original_id`
- 而按文书内语义签名生成

### 4.3 canonical 签名建议

推荐字段：

- `doc_id`
- `derived_type = SentencingCircumstance`
- `normalized_content`
- `polarity`
  - `mitigates / aggravates / neutral`
- `normative_kind`
  - `statutory / discretionary / unknown`
- `target_judgment_id` 或 `target_penalty_slot`

### 4.4 provenance 字段

- `source_record_ids`
- `source_original_ids`
- `payload_json_versions`
- `first_seen_at`
- `last_seen_at`

### 4.5 关系建议

- `DiscoveryRecord -[:PRODUCES_DERIVED_NODE]-> SentencingCircumstanceDerived`
- `SentencingCircumstanceDerived -[:MITIGATES]-> JudgmentResult`
- `SentencingCircumstanceDerived -[:AGGRAVATES]-> JudgmentResult`

过渡期兼容：

- 仍可使用 `RELATES_TO`，但 `relation_origin` 应标为 `discovery_derived`

## 5. EvidenceChain

### 5.1 语义定位

`EvidenceChain` 表示：

- 一组证据如何形成证明链
- 指向某个事实、结论或情节

它不是 `base` 正式实体，但也不是一次性临时节点。

### 5.2 模型结论

建议收口为：

- 文书级 canonical discovery derived node

推荐独立标签：

- `:DiscoveryDerivedNode`
  - `derived_type = EvidenceChain`

### 5.3 canonical 签名建议

推荐字段：

- `doc_id`
- `derived_type = EvidenceChain`
- `normalized_content`
- `ordered_evidence_refs`
- `target_entity_id`
- `chain_role`
  - `prove_fact`
  - `prove_circumstance`
  - `support_claim`
  - `other`

### 5.4 provenance 字段

- `source_record_ids`
- `source_original_ids`
- `edge_payload_versions`
- `payload_json_versions`

### 5.5 关系建议

- `DiscoveryRecord -[:PRODUCES_DERIVED_NODE]-> EvidenceChainDerived`
- `EvidenceChainDerived -[:SUPPORTS]-> Fact / SentencingCircumstance / Claim`
- `Evidence -[:CORROBORATES]-> Evidence`

注意：

- 证据之间的 `corroborates / contradicts` 仍可保留
- 但“这条链作为一个推理对象”应收口为单独稳定节点

## 6. ArgumentOutcome

### 6.1 语义定位

当前 `ArgumentOutcome` 更像有限状态值，而不是实体对象。

典型值：

- `采纳`
- `驳回`
- `部分采纳`

### 6.2 模型结论

推荐优先级：

1. 降为关系属性
2. 如必须保留结构化对象，则用受控枚举节点
3. 不建议继续作为普通 `DiscoveryNode`

### 6.3 推荐落法

首选：

- 在关系上挂：
  - `outcome = adopted / rejected / partial`

例如：

- `ArgumentPoint -[:SUPPORTS_CLAIM {outcome: "rejected"}]-> LitigationClaim`
- `ArgumentPoint -[:HAS_OUTCOME {outcome: "adopted"}]-> JudgmentResult`

次选：

- 全局受控词汇节点：
  - `:ArgumentOutcomeVocabulary {code: "adopted"}`

不推荐：

- 每条文书、每条 discovery record 各建一份 `DiscoveryNode(采纳/驳回)`

## 7. 推荐主键策略

### 7.1 base 复用类

- 使用 `base` 已有 `id`

### 7.2 文书级 discovery derived node

推荐统一：

- `derived_id = discovery_node:{doc_id}:{derived_type}:{semantic_digest}`

其中：

- `semantic_digest = sha1(canonical_signature)[:12]`

### 7.3 provenance 聚合

对已 canonical 化的派生节点，允许聚合：

- `source_record_ids`
- `source_original_ids`
- `source_count`

## 8. 推荐实施顺序

1. `LegalProvisionElement`
   - 先做强匹配复用
   - 再区分 `AppliedLegalProvisionElement`
2. `SentencingCircumstance`
   - 做文书级 canonical 收口
3. `EvidenceChain`
   - 做文书级 canonical 收口
4. `ArgumentOutcome`
   - 从节点降为关系属性或枚举值

## 9. 风险边界

### 9.1 不应过度自动复用

以下情况不要贸然复用：

- 文本归一化后命中多个 `base` 候选
- discovery 文本明显已带个案解释
- 缺乏法条上下文或目标实体上下文

### 9.2 不应让 derived node 退化成“无约束缓存节点”

如果保留为文书级派生节点，就必须：

- 有稳定 canonical id
- 有 provenance 聚合
- 有明确 derived_type

否则后续仍会重新回到“反复重复造节点”的旧问题

## 10. 本文结论

推荐最终落法如下：

- `LegalProvisionElement`
  - 强匹配复用 `base`
  - 解释性表达保留为 `AppliedLegalProvisionElement`
- `SentencingCircumstance`
  - 文书级 canonical discovery derived node
- `EvidenceChain`
  - 文书级 canonical discovery derived node
- `ArgumentOutcome`
  - 优先降为关系属性 / 枚举值

这是当前最符合“本体统一 + 发现层保留推理语义”的折中方案。

# 20260618_Neo4j开发任务拆解表

## 1. 文档目标

本文档用于把 Neo4j 接入 `remote-test` 的总体方案，进一步拆成可执行的开发任务阶段表。

目标是让后续开发可以直接按阶段排期、按角色分工、按验收口径推进。

本文档基于以下两份上游文档继续细化：

- [20260618_Neo4j接入方案与接口设计稿.md](file:///home/sxc/wendao/remote-test/docs/20260618_Neo4j接入方案与接口设计稿.md)
- [20260618_Neo4j落地接口与实施清单.md](file:///home/sxc/wendao/remote-test/docs/20260618_Neo4j落地接口与实施清单.md)

## 2. 总体实施分期

建议整体拆为 6 个阶段：

### 阶段 0：环境准备与基线校准

目标：

- 确保本地开发环境、Neo4j 环境、现有前后端链路都稳定可复现

### 阶段 1：文本块切分与对齐底座

目标：

- 在不破坏当前解析链的前提下，为文书建立 chunk 与结构节点对齐能力

### 阶段 2：Neo4j 基础写入能力

目标：

- 打通基础层图谱写入，至少支持 `Document + Chunk + Base Layer`

### 阶段 3：Workspace 基础交互接入

目标：

- 在 Workspace 中完成“基础图谱写入 Neo4j”的用户操作闭环

### 阶段 4：Retrieval / Discovery 图层写入

目标：

- 支持检索资产层和知识发现层的分层写入

### 阶段 5：Database 页面接入图数据库能力

目标：

- 在 Database 页面增加图数据库状态查看、差异比对和重载能力

## 3. 阶段 0：环境准备与基线校准

## 3.1 阶段目标

- 确认本地前后端环境稳定
- 确认后端使用仓库内 `ontology` 环境启动
- Neo4j 服务可以在本地或测试机正常连接
- 保证现有解析、保存、检索资产、深度思考不受影响

## 3.2 前置依赖

- 已有前端 Vite 环境可运行
- 已有后端 Flask 环境可运行
- 已有 `ontology` Python 环境
- 准备可用的 Neo4j 连接信息

## 3.3 后端任务

1. 新增 Neo4j 配置项规划
   - 设计 `.env` 中的 Neo4j 相关变量
   - 例如：
     - `NEO4J_URI`
     - `NEO4J_USER`
     - `NEO4J_PASSWORD`
     - `NEO4J_DATABASE`

2. 在后端增加 Neo4j 健康检查方案
   - 设计 `/api/neo4j/health` 或内部连通性检测函数

3. 梳理当前测试数据缓存结构
   - 明确 `_save_test_data()` 和 `_patch_test_data()` 后续扩展字段位

## 3.4 前端任务

1. 不做 UI 改动
2. 仅确认现有 Workspace 与 Database 页面正常可运行
3. 记录当前页面的稳定行为，作为后续回归基线

## 3.5 Neo4j schema 任务

1. 确认 Neo4j 版本
2. 确认是否使用默认数据库或独立数据库
3. 明确第一阶段最小 schema 范围：
   - `Document`
   - `Chunk`
   - `Fact`
   - `Evidence`
   - `ParseRun`
   - `IngestRun`

## 3.6 联调任务

1. 从后端机器测试 Neo4j 连通性
2. 验证 Python 驱动可建立 session
3. 验证不会影响现有 Flask 服务启动

## 3.7 验收任务

1. 前端服务正常
2. 后端服务正常
3. Neo4j 可连接
4. 现有 `/api/parse`、`/api/save`、`/api/deep-think` 不报错
5. 输出一份环境连通性记录

## 3.8 阶段交付物

- Neo4j 连接配置说明
- Neo4j 健康检查方案
- 当前环境基线说明

## 3.9 风险点

- Neo4j 连接权限问题
- 后端驱动安装和环境不一致
- 环境变量分散在多个项目环境中

## 4. 阶段 1：文本块切分与对齐底座

## 4.1 阶段目标

- 在当前解析链中加入 chunk 切分与对齐
- 保持整篇文书调用 LLM 的方式不变
- 让解析结果具备“反查原文块”的能力

## 4.2 后端任务

1. 新增 `backend/chunking.py`
   - 实现章节优先、段落次之、句子兜底的切分策略

2. 新增 `backend/alignment.py`
   - 实现解析结果到 chunk 的规则匹配

3. 改造 `backend/parser.py::parse_text()`
   - 在 `build_row_from_text()` 后增加切分
   - 在 `enrich_graph_output()` 后增加对齐
   - 返回 `text_chunks`、`source_alignment`、`chunking_meta`

4. 扩展 `backend/app.py::api_parse()`
   - 支持返回 chunk 相关字段

5. 扩展 `_save_test_data()` / `_patch_test_data()`
   - 允许缓存：
     - `text_chunks`
     - `source_alignment`
     - `chunking_meta`

6. 扩展 `api_save()`
   - 正式保存记录时允许保留 chunk sidecar

## 4.3 前端任务

1. 扩展 Workspace 启动回填逻辑
   - `loadTestData()` 后除 `json_result` 外，同时接住：
     - `text_chunks`
     - `source_alignment`

2. 扩展前端内存态
   - 增加对应 store 字段或 `TerminalPanel` 内部字段

3. 先不做大 UI
   - 可选：在 DetailPanel 或终端中增加临时调试显示

## 4.4 Neo4j schema 任务

本阶段只做设计和初始化准备，不要求真正写库。

1. 确认 `Chunk` 标签结构
2. 确认 `Document -> Chunk` 关系命名
3. 确认 chunk 主键约束：
   - `:Chunk(chunk_id)`

## 4.5 联调任务

1. 用同一篇案件文本调用 `/api/parse`
2. 确认返回：
   - `json_result`
   - `text_chunks`
   - `source_alignment`
3. 刷新页面后确认 `/api/test-data` 回填仍正常
4. 对比解析前后主图是否变化

## 4.6 验收任务

1. 解析成功率不下降
2. 前端主图不因为 chunk 字段新增而出错
3. 至少能对 `Fact`、`Evidence` 建立 chunk 映射
4. 测试数据与正式保存结构都能保留 chunk sidecar

## 4.7 阶段交付物

- `chunking.py`
- `alignment.py`
- 扩展后的 `/api/parse`
- 一份样例案件的 chunk / alignment 输出

## 4.8 风险点

- chunk 对齐命中率不稳定
- 过度修改 `json_result` 结构影响前端
- 不同案件文本格式导致切分效果波动

## 5. 阶段 2：Neo4j 基础写入能力

## 5.1 阶段目标

- 打通 Neo4j 的最小可用写入能力
- 支持基础层写入：
  - `Document`
  - `Chunk`
  - 基础结构节点
  - 基础结构关系
  - 节点到 chunk 的溯源关系

## 5.2 后端任务

1. 新增 `backend/neo4j_repository.py`
   - 封装驱动、session、事务执行

2. 新增 `backend/neo4j_service.py`
   - 实现基础层写入服务

3. 新增 `backend/neo4j_models.py`
   - 把 `json_result` 映射成图数据库写入 payload

4. 新增 `backend/neo4j_schema.py`
   - 管理约束初始化

5. 在 `backend/app.py` 新增接口：
   - `POST /api/neo4j/write-case`
   - `GET /api/neo4j/case-status/<doc_id>`
   - 可选：`GET /api/neo4j/health`

6. 实现 `IngestRun` 生成逻辑
7. 实现图层写入摘要返回逻辑

## 5.3 前端任务

本阶段前端只做最小调试入口，不做正式 UI。

1. `src/api/backend.js` 新增：
   - `writeNeo4jCase()`
   - `getNeo4jCaseStatus()`

2. 可选：
   - 在控制台或开发调试模式下临时调用该接口

## 5.4 Neo4j schema 任务

1. 创建唯一约束
   - `:Document(doc_id)`
   - `:Chunk(chunk_id)`
   - `:ParseRun(run_id)`
   - `:IngestRun(run_id)`
   - `:Fact(id)`
   - `:Evidence(id)`
   - 其他第一批节点标签约束

2. 确认第一批关系：
   - `HAS_CHUNK`
   - `HAS_ENTITY`
   - `SUPPORTED_BY_CHUNK`
   - `PROVES`
   - `GENERATED_BY_PARSE_RUN`
   - `INGESTED_BY`

3. 输出可执行初始化脚本或初始化函数

## 5.5 联调任务

1. 手工拿一篇案件：
   - 先 `/api/parse`
   - 再 `/api/neo4j/write-case`

2. 校验写入结果：
   - Neo4j 浏览器能查到 `Document`
   - 能查到对应 `Chunk`
   - 至少有一类基础节点
   - 至少有一条溯源关系

3. 调用 `GET /api/neo4j/case-status/<doc_id>`
   - 确认状态正确返回

## 5.6 验收任务

1. `write-case` 接口可稳定调用
2. 重复写入同一案件不会无控制重复创建
3. 能看到 `base` 层写入摘要
4. 不影响原有 `/api/save` 和 JSONL 保存

## 5.7 阶段交付物

- Neo4j repository / service / schema 模块
- 基础写入接口
- 基础约束初始化方案
- 一份基础写入样例查询结果

## 5.8 风险点

- 业务对象映射粒度不统一
- 关系 ID 设计不稳导致重复边
- 失活策略和覆盖策略定义不清

## 6. 阶段 3：Workspace 基础交互接入

## 6.1 阶段目标

- 在 Workspace 内形成“解析完成 -> 点击按钮 -> 写入 Neo4j -> 看见状态”的完整闭环

## 6.2 后端任务

1. 补充 `write-case` 错误码与返回结构
2. 如果需要，支持根据 `row_id` 自动推导 `doc_id`
3. 支持把写入状态回填到测试缓存结构中

## 6.3 前端任务

1. 在 `TerminalPanel.js` 保存区新增按钮：
   - `写入 Neo4j`

2. 新增函数：
   - `handleWriteNeo4jBase()`

3. 在 `src/api/backend.js` 中实现：
   - `writeNeo4jCase()`

4. 扩展前端状态：
   - `neo4jStatus`
   - `neo4jLastWriteSummary`
   - `neo4jLastRunId`

5. 在状态栏展示：
   - `Neo4j: 未写入 / 已写入基础层`

6. 若页面刷新后需要保留状态：
   - 从 `/api/test-data` 或状态接口恢复

## 6.4 Neo4j schema 任务

1. 不新增核心标签
2. 仅根据实际写入需要补索引
3. 校验当前 schema 足够支撑 Workspace 基础写入

## 6.5 联调任务

1. 在真实页面中完成以下流程：
   - 输入原文
   - 点击解析
   - 点击写入 Neo4j

2. 观察：
   - 按钮 loading 状态
   - 成功提示
   - 状态栏更新
   - 页面刷新后状态恢复

## 6.6 验收任务

1. 用户在 Workspace 能明确感知写入成功与否
2. 成功后状态可见
3. 失败时错误信息可见
4. 不破坏当前保存按钮逻辑

## 6.7 阶段交付物

- Workspace 基础写入按钮
- 基础图数据库状态显示
- 前端状态恢复方案

## 6.8 风险点

- UI 状态过多导致逻辑混乱
- 文书 `doc_id` 生成规则前后端不一致
- 页面刷新后本地状态和图数据库状态不一致

## 7. 阶段 4：Retrieval / Discovery 图层写入

## 7.1 阶段目标

- 支持在基础层之外，把检索资产层和知识发现层独立写入 Neo4j

## 7.2 后端任务

1. 在 `neo4j_models.py` 中新增：
   - `build_retrieval_layer_payload()`
   - `build_discovery_layer_payload()`

2. 在 `neo4j_service.py` 中新增：
   - `write_retrieval_layer()`
   - `write_discovery_layer()`

3. 在 `app.py` 新增接口：
   - `POST /api/neo4j/write-retrieval-layer`
   - `POST /api/neo4j/write-discovery-layer`

4. 为 retrieval / discovery 返回独立写入摘要
5. 更新 `case-status` 接口，使其能返回三层状态：
   - `base`
   - `retrieval`
   - `discovery`

## 7.3 前端任务

1. Retrieval 区域新增按钮：
   - `写入检索层`

2. 新增函数：
   - `handleWriteRetrievalLayer()`

3. Discovery 区域新增按钮：
   - `写入发现层`

4. 新增函数：
   - `handleWriteDiscoveryLayer()`

5. 扩展状态展示：
   - `Neo4j: 基础层已写入 / 检索层已写入 / 发现层已写入`

## 7.4 Neo4j schema 任务

1. 补充分层相关属性规范：
   - `graph_layer`
   - `source_pipeline`
   - `source_run_id`

2. 如有必要，新增运行时层的关系约束或索引

3. 明确 Retrieval / Discovery 是否复用基础实体节点
   - 若复用，定义复用规则
   - 若不复用，定义隔离规则

## 7.5 联调任务

1. 完成 Retrieval 流程：
   - 生成检索资产
   - 点击写入检索层
   - 查看状态变化

2. 完成 Discovery 流程：
   - 执行深度思考
   - 点击写入发现层
   - 查看状态变化

3. 核验三个图层互不污染

## 7.6 验收任务

1. `base / retrieval / discovery` 三层状态可独立显示
2. 写入检索层不会覆盖基础层
3. 写入发现层不会污染基础层
4. 重复写入同层时有可预期覆盖或失活规则

## 7.7 阶段交付物

- Retrieval 层写入接口
- Discovery 层写入接口
- Workspace 三层写入能力
- 三层状态展示

## 7.8 风险点

- retrieval bundle 和基础图节点映射口径不一致
- discovery 输出结构不稳定
- 图层边界不清导致同一节点被多层错误覆盖

- 图数据库返回结构与现有详情视图不兼容

### 角色 B：Neo4j 服务层

负责：

- `neo4j_repository.py`
- `neo4j_service.py`
- `neo4j_schema.py`

### 角色 C：Workspace 前端

负责：

- 基础层写入按钮
- Retrieval / Discovery 写入按钮
- 状态展示

### 角色 D：Database 前端

负责：

- 图数据库 Tab
- 差异对比入口
- 重载 / 重同步入口

### 角色 E：联调与验收

负责：

- 接口联调
- 样例案件通路验证
- 回归现有解析、保存、检索、深度思考链路

## 10. 统一验收口径

为了避免每阶段验收标准不一致，建议统一遵循以下口径：

### 功能正确

- 接口能按设计返回
- 前端按钮能正常触发
- Neo4j 中的结果能查询到

### 行为不回退

- 不影响当前 `/api/parse`
- 不影响当前 `/api/save`
- 不影响当前 retrieval bundle 工作流
- 不影响当前深度思考工作流

### 状态可观察

- 成功有成功提示
- 失败有失败提示
- 写入状态可查

### 数据可追踪

- 至少基础层具备：
   - 文书根节点
   - chunk
   - 实体
   - 溯源关系

### 可重复执行

- 同一案件重复写入不会生成不可控脏数据

## 11. 推荐实施顺序总结

如果按风险最低、收益逐步释放的顺序推进，推荐如下：

1. 阶段 0：环境准备与基线校准
2. 阶段 1：文本块切分与对齐底座
3. 阶段 2：Neo4j 基础写入能力
4. 阶段 3：Workspace 基础交互接入
5. 阶段 4：Retrieval / Discovery 图层写入
6. 阶段 5：Database 页面接入图数据库能力

这样安排的好处是：

- 每个阶段都能独立交付
- 每个阶段都能单独验收
- 任一阶段出问题都能回到上一稳定状态

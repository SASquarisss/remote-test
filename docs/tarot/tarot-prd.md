# 塔罗牌占卜网站 PRD（首版 Demo）

## 1. 项目定位

### 1.1 项目名称
塔罗占卜网站 Demo

### 1.2 项目目标
基于现有 Demo UI，设计一个可完成“输入问题 -> 选择牌阵 -> 抽牌 -> AI 解读 -> 获取建议”的线上塔罗占卜体验闭环，用于首版产品验证。

### 1.3 首版目标
1. 让用户快速完成一次完整占卜体验。
2. 建立神秘、沉浸、有仪式感的视觉与交互氛围。
3. 通过 AI 生成具有个性化的塔罗解读内容。
4. 支持匿名使用，无需登录即可体验。
5. 为后续商业化能力预留扩展位。

### 1.4 非目标
1. 首版不做账号体系。
2. 首版不做云端历史记录。
3. 首版不做复杂社区、分享、社交玩法。
4. 首版不承诺专业心理咨询、医疗、法律、投资建议。

## 2. 已确认需求

根据当前沟通，首版产品约束如下：

1. 交付内容以产品设计文档为主，暂不要求直接开发代码。
2. 解读内容由 AI 生成，不采用纯规则模板输出。
3. 用户默认匿名使用，不登录即可完成占卜。
4. 首版仅需单次体验闭环，不保存云端历史。
5. 产品暂不直接上线付费，但需为高级牌阵、深度解读等能力预留商业化入口。
6. 抽牌方式采用系统随机抽牌。
7. 占卜问题支持自由输入，仅做基础输入规范控制。
8. 解读文案风格偏神秘仪式感。

## 3. Demo 还原与交互理解

根据截图，当前 Demo 可拆为 3 个核心页面。

### 3.1 页面一：占卜入口页

页面结构：
1. 顶部品牌区
   - 标题：塔罗占卜
   - 副标题：选择牌阵，探索内心的智慧
2. 问题输入区
   - 标题：请输入您的占卜问题
   - 文案提示：详细的问题将帮助获得更精准的解读
   - 输入框示例：我应该如何处理当前的工作困境？我的感情发展会如何？
3. 牌阵选择区
   - 三牌阵：过去 / 现在 / 未来
   - 凯尔特十字牌阵
   - 七行星牌阵

交互理解：
1. 用户先输入问题。
2. 用户浏览不同牌阵说明，选择一种牌阵。
3. 点击牌阵卡片后，进入该牌阵的抽牌流程页。

### 3.2 页面二：抽取卡牌页

页面结构：
1. 页面标题：抽取卡牌
2. 副标题：点击卡牌进行抽取
3. 牌位容器区
   - 示例中展示三牌阵的 3 个牌位：过去、现在、未来
   - 已抽到的牌展示牌面、名称、元素或花色、简要说明
   - 未抽牌位保持空态
4. 剩余卡牌提示
   - 示例文案：剩余卡牌：1
5. 牌库区
   - 多张背面朝上的卡牌，以整齐矩阵形式展示
   - 用户点击任一牌背完成一次抽取

交互理解：
1. 用户选定牌阵后，进入对应牌阵的抽牌页。
2. 页面根据该牌阵的牌位数量生成若干占位框。
3. 用户每点击一次牌背，系统从牌库中随机抽取 1 张牌，并随机生成正位或逆位。
4. 抽中的牌按顺序填入当前待抽牌位。
5. 当所有牌位填满后，系统解锁“开始解读”或自动跳转解读页。

### 3.3 页面三：解读结果页

页面结构：
1. 页面标题：塔罗解读
2. 副标题：卡牌的智慧指引
3. 本次牌阵标题
   - 示例：三牌阵深度解读
4. 用户问题回显区
5. 单牌解读区
   - 每张牌一张卡片
   - 展示：牌名、正逆位、牌位名称、牌位说明
   - 展示维度：核心含义、情境分析、元素指引、星象影响、位置指导
6. 综合分析区
   - 能量流动分析
   - 冲突与和谐
   - 时机与周期
   - 元素能量分布
7. 深度整合建议区
   - 当前状况总结
   - 关键行动指导
   - 长期发展建议
8. 底部按钮
   - 新的占卜

交互理解：
1. 当抽牌完成后，系统使用“问题 + 牌阵 + 各牌信息”生成整套解读。
2. 结果先展示每张牌的单独解释，再给出全局总结。
3. 用户可点击“新的占卜”返回首页重新开始。

## 4. 核心用户流程

### 4.1 主流程
1. 用户进入首页。
2. 输入占卜问题。
3. 选择牌阵。
4. 进入抽牌页。
5. 逐张点击牌背抽牌。
6. 全部牌位抽满。
7. 系统生成 AI 解读。
8. 用户查看结果与建议。
9. 用户发起新的占卜。

### 4.2 页面跳转规则
1. 首页未输入问题时，牌阵卡片可点击，但点击后需进行校验提醒。
2. 若问题为空，提示“请先输入你想咨询的问题”。
3. 校验通过后进入抽牌页。
4. 抽牌完成后进入结果页。
5. 结果页点击“新的占卜”返回首页并清空本次会话。

## 5. 业务规则设计

### 5.1 占卜问题规则
1. 支持自由文本输入。
2. 建议字数范围：6 到 120 字。
3. 少于 6 字时提示用户补充，以便 AI 生成更有针对性的解读。
4. 超过 120 字时提示精简问题。
5. 过滤明显违法、暴力、仇恨、色情等内容。
6. 对涉及自残、自杀、严重精神危机的内容，不进入常规占卜流程，改为安全提示与求助引导。

建议提示文案：
1. 输入过短：请更具体地描述你的问题，以便获得更准确的指引。
2. 输入过长：问题略长，请聚焦一个核心困惑。
3. 风险问题：当前问题不适合使用占卜给出判断，建议优先寻求专业帮助。

### 5.2 牌阵规则

#### 5.2.1 三牌阵
定位：轻量、快速、适合日常问题。

牌位定义：
1. 过去：问题形成背景、既往影响。
2. 现在：当前处境、核心矛盾、正在发生的能量。
3. 未来：趋势走向、建议方向、潜在结果。

抽牌数量：3 张。

#### 5.2.2 凯尔特十字牌阵
定位：复杂问题深度分析。

建议规则：
1. 若产品名称为“凯尔特十字牌阵”，标准应为 10 张牌。
2. 当前 Demo 文案中出现“13 张牌阵”，与常见认知不一致，建议产品统一。
3. 若要坚持 13 张，应改名为扩展牌阵，避免与传统凯尔特十字混淆。

首版建议：
1. 文案改为“经典 10 张深度牌阵”。
2. 上线时优先使用标准 10 张结构。

#### 5.2.3 七行星牌阵
定位：周期趋势、阶段运势、人生维度分析。

建议牌位方向：
1. 自我状态
2. 情感关系
3. 事业发展
4. 财富能量
5. 行动力
6. 外部影响
7. 总体走向

抽牌数量：7 张。

### 5.3 牌库规则
1. 首版默认使用完整 78 张塔罗牌库。
2. 每次占卜开始时，初始化一个独立牌库。
3. 同一轮占卜内，已抽出的牌不可重复抽中。
4. 每次抽中后，从剩余牌堆移除该牌。
5. 正位 / 逆位独立随机生成。

推荐随机逻辑：
1. 抽牌：从剩余牌库中均匀随机选择 1 张。
2. 正逆位：50% 正位，50% 逆位。

### 5.4 抽牌展示规则
1. 用户点击任意牌背，本质都是触发一次随机抽牌，不要求用户“真实挑中某一张具体牌”。
2. 为保持仪式感，可保留牌阵中的视觉牌背矩阵。
3. 点击后建议加入翻牌动画，再将结果填入对应牌位。
4. 当前待抽牌位建议高亮，降低用户理解成本。
5. 抽满前不可查看最终解读。

### 5.5 AI 解读规则
AI 输入信息建议包含：
1. 用户原始问题。
2. 选择的牌阵类型。
3. 各牌位名称与含义。
4. 抽中的牌名。
5. 每张牌的正位 / 逆位。
6. 每张牌的基础牌义标签。
7. 输出风格设定：神秘、仪式感、启发式，不做绝对预测。

AI 输出结构建议固定为：
1. 总体引言
2. 单牌解读
3. 多牌联动分析
4. 风险或阻碍
5. 行动建议
6. 长期提醒

输出限制：
1. 不得输出确定性命运宣判。
2. 不得鼓励极端决定。
3. 不得替代医疗、法律、投资专业意见。
4. 对高风险问题优先输出关怀与求助建议。

### 5.6 结果页展示规则
1. 每张牌都必须展示牌位信息与正逆位。
2. 每张牌的单独解读应与用户问题强关联，而非纯百科式释义。
3. 综合分析需体现多张牌之间的关联，而不是单卡解读的简单拼接。
4. 行动建议要给出可执行表达，例如“在未来一周内尝试…”。
5. 若用户问题过于模糊，结果页需提示“本次解读基于较宽泛的问题，建议下次聚焦一个主题”。

## 8. 推荐状态机

### 8.1 会话状态
1. `idle`：未开始。
2. `question_ready`：已输入有效问题。
3. `spread_selected`：已选择牌阵。
4. `drawing`：进行抽牌中。
5. `draw_complete`：抽牌完成。
6. `reading_generating`：AI 解读生成中。
7. `reading_ready`：解读结果可查看。
8. `error`：异常状态。

### 8.2 关键状态约束
1. 未完成抽牌前，不可触发解读生成。
2. 解读生成中，不可重复发起请求。
3. 刷新页面后，若首版不做会话恢复，则可直接重置流程。

## 10. AI 解读产品设计

### 10.1 解读目标
1. 提供足够个性化的回答。
2. 兼顾神秘感、启发性与可读性。
3. 保持结构统一，便于页面稳定展示。

### 10.2 推荐 Prompt 组成
1. System Prompt
   - 设定角色为具有神秘仪式感的塔罗解读者。
   - 语气温和、深邃、启发式。
   - 强调趋势与建议，不做绝对命运判断。
2. Context Prompt
   - 注入牌阵说明、牌位含义、牌义知识库。
3. User Prompt
   - 注入用户问题与本次抽牌结果。
4. Output Format Prompt
   - 强制输出结构化 JSON 或固定分段文本。

### 10.3 推荐输出字段
1. `opening_message`
2. `card_readings`
3. `overall_analysis`
4. `energy_flow`
5. `conflict_and_harmony`
6. `timing_hint`
7. `action_advice`
8. `long_term_advice`
9. `safety_notice`

### 10.4 风格规范
1. 可用“命运之轮正在缓慢转动”这类仪式感表达。
2. 避免“你一定会”“绝对会发生”这类确定性句式。
3. 优先使用“当前趋势显示”“这张牌提示你留意”。
4. 建议控制在可读范围内，避免一味堆砌玄学辞藻。

## 11. 异常与边界场景

### 11.1 输入类异常
1. 问题为空。
2. 问题过短或过长。
3. 命中敏感内容。

### 11.2 抽牌类异常
1. 用户中途离开页面。
2. 抽牌请求失败。
3. 牌库状态异常导致重复牌。

处理建议：
1. 本地缓存当前会话 10 分钟。
2. 失败后允许重试当前抽牌动作。
3. 出现重复牌时直接废弃本次结果并重新生成抽牌结果。

### 11.3 AI 类异常
1. 模型超时。
2. 模型返回格式不合法。
3. 文案为空或过短。

处理建议：
1. 提供“重新生成解读”按钮。
2. 失败时先展示兜底文案。
3. 对输出做格式校验与内容清洗。

## 12. 商业化预留设计

虽然首版不直接收费，但建议预留以下能力：

1. 高级牌阵入口
   - 首页部分牌阵可标记“深度解读”或“即将开放”。
2. AI 深度版解读
   - 免费版展示基础结果，后续可升级更长篇、更细致分析。
3. 占卜报告导出
   - 预留 PDF 或图片长图导出。
4. 历史记录
   - 未来与登录体系结合，支持回看往期占卜。
5. 专题占卜
   - 感情、事业、财运专题版解读模板。

## 13. UI 与内容风格要求

### 13.1 视觉风格
1. 深紫色夜空背景。
2. 金色描边与高亮元素。
3. 微弱粒子或星尘效果，强化神秘氛围。
4. 卡片与容器使用轻微发光效果。

### 13.2 文案风格
1. 整体偏神秘仪式感。
2. 避免过度冰冷的工具化语言。
3. 标题尽量有召唤感、指引感、洞察感。
4. 正文强调“启示”“趋势”“能量”“阶段”。

## 14. 验收标准

首版文档对应的产品验收标准建议如下：

1. 用户可在 3 步内进入抽牌流程。
2. 用户可完成至少一种牌阵的完整占卜。
3. 抽牌结果不重复，且可识别正逆位。
4. AI 解读内容结构完整，可直接渲染到结果页。
5. 结果内容与用户问题、牌阵、牌位三者有关联。
6. 高风险问题可被识别并触发安全提示。
7. 首页与结果页均有清晰返回和重新开始路径。

## 15. 当前发现的问题与建议

### 15.1 Demo 文案一致性问题
1. “凯尔特十字牌阵”与“13 张牌阵”存在命名冲突，需统一。
2. 不同牌阵卡片建议补充“适用场景”字段，提升选择效率。

### 15.2 交互优化建议
1. 首页选择牌阵前，可提示“先写下你此刻最想问的问题”。
2. 抽牌页建议高亮当前正在抽取的牌位。
3. 解读生成阶段建议加入仪式感 loading 文案，例如“群星正在为你排列答案...”。
4. 结果页建议支持“重新解读”与“新的占卜”两个动作分离。

## 16. 首版建议范围（MVP）

为尽快落地，建议 MVP 仅包含：

1. 首页问题输入。
2. 三牌阵完整体验。
3. 随机抽牌与正逆位。
4. AI 结果页输出。
5. 基础安全校验。

第二阶段再扩展：
1. 七行星牌阵。
2. 凯尔特十字牌阵。
3. 本地历史记录。
4. 商业化试探入口。

## 17. 结论

这个 Demo 已经具备清晰的产品骨架，核心业务闭环明确，适合以“三牌阵 + AI 解读”作为首版 MVP 快速验证。产品重点不在复杂功能数量，而在三件事：

1. 抽牌过程是否有仪式感。
2. AI 解读是否足够贴题且有神秘氛围。
3. 用户是否愿意继续进行下一次占卜或尝试更深层牌阵。

1. 信息架构 + 页面原型说明稿。

## 18. 前后端接口设计

### 18.1 设计原则
在“匿名单次体验、不记录历史、不需要账号”的前提下，首版接口设计遵循以下原则：

1. 前端只负责页面状态、抽牌交互和结果展示。
2. 后端负责牌阵配置下发、抽牌结果生成、AI 解读生成、内容安全控制。
3. 不依赖用户登录态。
4. 不要求数据库持久化会话结果。
5. 所有流程围绕一次性占卜会话展开。

### 18.2 推荐流程拆分

#### 方案 A：推荐方案
由后端负责“初始化会话 -> 抽牌 -> 生成解读”。

优点：
1. 抽牌逻辑统一，避免前端被篡改。
2. AI 输入结构稳定。
3. 后续如果加入付费、历史、风控，更容易扩展。

#### 方案 B：极简方案
前端本地完成抽牌，后端仅接收最终抽牌结果并生成 AI 解读。

优点：
1. 开发速度更快。
2. 后端接口更少。

缺点：
1. 抽牌结果可信度较弱。
2. 后续接入风控、支付、历史记录时需要重构。

首版建议采用方案 A。

### 18.4 前端调用顺序
1. 首页加载时调用 `GET /api/v1/spreads`。
2. 用户选择牌阵后，调用 `POST /api/v1/divinations` 创建会话。
3. 抽牌页每点击一次牌背，调用 `POST /api/v1/divinations/{sessionId}/draw`。
4. 抽牌完成后，调用 `POST /api/v1/divinations/{sessionId}/reading`。
5. 若做刷新恢复，则页面进入时调用 `GET /api/v1/divinations/{sessionId}`。

### 18.5 前端本地状态建议
即使不落库，前端仍建议保存以下临时状态：

1. `session_id`
2. `question`
3. `spread_id`
4. `drawn_cards`
5. `reading_status`

建议存储位置：
1. React state 或 Vue state
2. `sessionStorage`

建议：
1. 若只要求单页流转，可仅放内存状态。
2. 若要支持刷新恢复，放入 `sessionStorage` 即可。

## 19. 数据库表结构建议

### 19.1 先回答核心结论
如果当前明确是：

1. 不记录历史
2. 不需要账号
3. 不做支付
4. 不要求后台运营查看用户占卜记录
5. 不要求跨设备恢复会话

那么首版严格来说可以“不上业务数据库”。

也就是说：
1. 牌库数据可以直接放在后端配置文件或 JSON 文件中。
2. 牌阵配置也可以直接写在配置文件中。
3. 占卜会话可以仅保存在服务内存或前端 `sessionStorage` 中。
4. AI 解读可以实时生成后直接返回，不做持久化。

这是当前需求下的最小实现。

### 19.2 如果完全不使用数据库
推荐资源组织方式：

1. `cards.json`
   - 存 78 张牌的基础信息
2. `spreads.json`
   - 存牌阵及牌位定义
3. 服务内存中的 `session_store`
   - 存 10 到 30 分钟内的匿名会话

适用场景：
1. 只是 Demo
2. 用户量小
3. 可以接受服务重启后会话丢失

### 19.3 如果要“最小可用数据库”
如果你希望：

1. 页面刷新后还能恢复会话
2. 服务重启后不丢当前正在占卜的状态
3. 后续平滑扩展到历史记录、付费、风控

那么建议最少只建 1 张业务表：

#### 表 1：`divination_session`
用途：
保存匿名占卜的临时会话。

字段建议：

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `id` | varchar(32) | 会话 ID |
| `question` | text | 用户输入的问题 |
| `spread_id` | varchar(50) | 牌阵 ID |
| `status` | varchar(30) | `drawing` / `draw_complete` / `reading_ready` / `error` |
| `drawn_cards_json` | json | 已抽卡结果 |
| `reading_json` | json | AI 解读结果 |
| `expires_at` | datetime | 会话过期时间 |
| `created_at` | datetime | 创建时间 |
| `updated_at` | datetime | 更新时间 |

说明：
1. `drawn_cards_json` 直接存数组，避免首版拆多表。
2. `reading_json` 直接存结果，便于刷新恢复。
3. 通过 `expires_at` 定时清理，不形成长期历史。

这是我对你当前需求下最推荐的“最小表结构”。

### 19.4 哪些表当前不需要
在现阶段，下列表都不是必须的：

1. `user`
2. `user_profile`
3. `order`
4. `payment`
5. `history`
6. `favorite_spread`
7. `membership`
8. `drawn_card_detail`

### 19.5 牌库和牌阵要不要建表
当前阶段不建议一开始就建表。

原因：
1. 牌库和牌阵是低频变更的静态基础数据。
2. 用配置文件维护更快。
3. 更适合 Demo 和早期迭代。

只有在以下情况再考虑建表：
1. 需要后台运营动态修改牌阵。
2. 需要多语言管理。
3. 需要在线配置 AI 文案模板。
4. 需要做复杂版本管理。

若未来要建，可拆为：
1. `tarot_card`
2. `spread`
3. `spread_position`

### 19.6 推荐的两档方案

#### 档位 1：Demo 极简版
不使用数据库。

实现方式：
1. 牌库和牌阵放 JSON。
2. 前端保存 `session_id` 和当前流程状态。
3. 后端按请求实时生成抽牌结果和 AI 解读。

#### 档位 2：可上线试运行版
使用 1 张 `divination_session` 表。

实现方式：
1. 牌库和牌阵仍放 JSON 或代码配置。
2. 只把匿名会话落库。
3. 会话按过期时间自动清理。

### 19.7 当前我的明确建议
结合你现在的需求，我建议：

1. 如果只是先做前端 Demo 联调，用“无数据库方案”。
2. 如果你准备很快进入可访问的测试环境，用“1 张 `divination_session` 表方案”。
3. 不要现在就设计账号、历史记录、支付相关表。

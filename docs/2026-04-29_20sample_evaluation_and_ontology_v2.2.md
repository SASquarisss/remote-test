## 2. 失败样本根因分析

| ID | case_type | 根因 | 是否正常 |

| 5419 | 刑事-抢劫罪 | 文本包含"是否应该适用禁止令"的争议，LLM 忽略 | ✗ LLM 错误 |
| 3692 | 民事-环境污染责任纠纷 | 文本包含因果关系、责任分配争议，LLM 忽略 | ✗ LLM 错误 |

**结论**：50% 的空值是正常的（非诉讼案件无争议焦点），50% 是 LLM 提取缺失。

### 2.2 judgment_result / guiding_points 为空（1 条）

| ID | case_type | 根因 |
|---|---|---|
| 3692 | 民事-环境污染责任纠纷 | judgment_reason 长达 2517 字，judgment_essence 长 122 字，两者均有明确内容，LLM 完全未提取。属于典型的 LLM 幻觉失败。 |

judgment_essence 原文：
> 在无意思联络数人环境侵权案件中，存在多个污染源头和多次污染行为时，可从空间和时间两个维度入手，结合自然规律、地域区位等因素认定单次污染行为与损害后果的因果关系。当事人之间就单次环境污染的损害后果达成的赔偿协议并不免除侵权人应当承担的修复责任。

**结论**：这是一个明确的 LLM 提取失败。原因可能是：
1. judgment_reason 过长（2517 字），LLM 在处理长文本时忽略了末尾的结论部分
2. 文本中没有明确的"裁判结果"、"判决"等标记，而是以推理分析为主，LLM 难以分辨哪部分是结果

### 2.3 legal_provisions 为空（14 条）

根据对 7 条"双空"（LLM 和正则均未提取到）样本的深度分析：

| ID | case_type | 文本中是否有显式法条引用 | 根因 |
|---|---|---|---|
| 12194 | 民事-侵权/司法救助 | 否 | 司法救助案件，无需引用具体法条 |
| 12768 | 空/司法救助 | 否 | 司法救助案件 |
| 6599 | 民事-租赁/调解 | 否 | 调解案件，无法条引用 |
| 6295 | 民事-物业/调解 | 否 | 调解案件 |
| 868 | 民事-房屋买卖 | 否 | 诉讼案件，但法官在判决理由中未明确引用法条，仅通过事实分析和证人证言推理 |
| 3692 | 民事-环境污染 | 否 | 诉讼案件，判决理由详细分析因果关系和责任分配，未明确引用《侵权责任法》/《民法典》具体条文 |
| 5419 | 刑事-抢劫罪 | 否 | 诉讼案件，判决理由提及"抢劫罪"和"禁止令"，但未明确写出《刑法》第 263 条、第 38 条等具体条号 |

**结论**：在这 7 条样本中，文本字段（basic_facts / judgment_reason / judgment_essence / related_law / judgment_mean）**真的不包含显式法条引用**。其中：
- 4 条是非诉讼案件（调解/司法救助），正常
- 3 条是诉讼案件但法官未在提供的文本中明确引用法条（中国法院判决书常见现象）

这意味着：
1. **正则补提上限有限**——只能提取文本中**显式引用**的法条，无法推断隐含法条
2. **LLM 补提也有限**——当文本本身不包含法条时，LLM 也无法"凭空"提取
3. **要达到 80% 填充率，必须依赖案件类型 → 典型法条映射**（如"抢劫罪" → 刑法第 263 条）

## 3. 正则补提模块

已创建 `scripts/extract_legal_provisions_regex.py`，支持：
- 完整格式：《中华人民共和国XX法》第一百二十条之一第三款第四项
- 简写格式：XX法第一百二十条
- 司法解释：最高人民法院/最高检 关于...的解释/规定/批复
- 依据式引用（无条号）：依据/根据/按照《XX法》

在 20 条样本上的表现：
- 补提率：**5.0%** (1/20)
- 主要价值：捕获 LLM 忽略的**显式引用**（如司法解释）
- 与 LLM 结果合并时使用 `(statute, article, paragraph)` 三元组去重

## 4. 本体论 v2.2 优化内容

基于 20 条样本分析，发现案件形态差异化远超预期，原版本体论假设所有记录均为法院诉讼案件。实际数据包含：
- 诉讼案件（12条）
- 调解案件（4条）
- 仲裁案件（1条）
- 司法救助案件（2条）

### 4.1 实施变更

| 变更项 | 说明 |
|---|---|
| `LegalRole.role_enum` +3 | `mediator` (调解员), `arbitrator` (仲裁员), `beneficiary` (被救助人/受益人) |
| `CaseParticipant.role_code_enum` +3 | 同上 |
| `JudgmentResult.result_type_enum` +3 | `mediation_agreement` (调解协议), `arbitration_award` (仲裁裁决), `administrative_decision` (行政决定) |
| `CourtCase` 新增字段 | `dispute_resolution_type`: `litigation | mediation | arbitration | judicial_aid | administrative_review` |
| `CourtCase.case_number` | 由 **必填**改为 **可选**，移除严格正则验证 |

### 4.2 提取提示词更新

`scripts/prompts/guiding_case_extraction.txt` 已同步更新：
- 当事人角色增加了 `mediator` 和 `beneficiary` 的说明
- 裁判结果类型增加了 `mediation_agreement`, `arbitration_award`, `administrative_decision` 及其定义
- 案号/法院提取规则增加了注意事项：调解、仲裁、司法救助案件可能没有法院案号

## 5. 后续建议

### 5.1 短期（下一轮小样本）

1. **法条补充策略**：正则 + LLM 已是上限，需要引入案件类型 → 典型法条映射表，建议先在 50 条样本上验证
2. **LLM 提取可靠性**：建议增加对长文本的分段处理（将 judgment_reason 按段落切片后分批输入 LLM）
3. **调解/仲裁/救助案件识别**：当前依赖 LLM 判断，可考虑用关键词规则预分类（如"调解员"、"仲裁庭"、"司法救助"）

### 5.2 中期（生产级打通）

1. **多模型集成**：deepseek-v4-pro 用于核心提取，轻量模型（如 qwen-14b）用于法条补提和格式校验
2. **人工审核队列**：将 `judgment_result` 和 `guiding_points` 为空的记录自动标记为低置信度，进入人工审核
3. **法条库对接**：将提取到的法条与正式法条库校验，校验通过后才导入图谱

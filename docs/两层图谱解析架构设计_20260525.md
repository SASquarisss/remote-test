# 两层图谱解析架构设计（草案）

## 1. 核心痛点：本体爆炸与领域泛化

在法律知识图谱的构建中，由于各种案件（如刑事走私、民事离婚、交通事故等）事实极其多变且复杂，如果试图用同一套详尽的底层关系边（如 `雇佣`、`汇款给`、`碰撞`）和特定的物理实体（如 `摄影器材`、`毒品`）来穷尽所有案件事实，将不可避免地导致：
- **本体爆炸（Schema Explosion）**：关系种类无休止地增长。
- **解析崩溃**：大语言模型（LLM）难以在复杂的泛化选项中做出准确提取，引发解析断链。
- **图谱不可维护**：展示逻辑将极度杂乱，且不同案由间的架构不通用。

## 2. 解决方案：两层图谱解析架构（双层抽象）

为了在保持核心法律逻辑清晰的同时，不丧失具体案由微观事实的表现力，系统采用“两层解析架构（Core-Schema + Sub-Schema）”范式：

### 第一层：通用法律程序网络（Core Legal Ontology）
本层为所有案件的**兜底通用结构**，关注标准化的司法流程和法律逻辑闭环。
- **核心实体**：当事人（LegalSubject）、事实容器（Fact）、证据（Evidence）、法条（LegalProvision）、控辩主张（LitigationClaim）、裁判情节（LegalCircumstance）、裁判结果（JudgmentResult）。
- **设计原则**：
  - **事实中心化（Fact as a Hub）**：将具体的社会关系（如谁指使谁）降维成自然语言存放在 `Fact` 文本中，边缘人物通过通用边 `involved_in_fact` 挂载到事实节点。
  - **财产属性化（Attribute over Entity）**：涉案金额、标的物等均作为 `CaseSummary` 或特定节点的属性，不作为独立节点抽取，以免导致时间链混乱。
- **优势**：保证系统的鲁棒性，所有案件的宏观可视化逻辑保持统一。

### 第二层：定制化领域事件网络（Event Sub-graph / Domain Schema）
本层针对特定案由进行**微观事件插拔**，解决细节溯源和定制化分析需求。（暂为规划阶段，后续按需开发）
- **核心逻辑**：
  - 当解析器识别出特定案件类型（如“走私案”）时，系统动态加载特定的领域子图谱 Schema（如 `Smuggling_Ontology.yaml`）。
  - 该子图中允许定义微观的实体和动作边（例如 `[走私头目] -雇佣-> [水客] -运输-> [走私货物] -途经-> [口岸]`）。
- **优势**：
  - 作为第一层图谱的补充。在前端展示时，作为独立的“案件重演视图”或“犯罪网络图”，与主法律图谱隔离展示，从而避免污染全局的核心图谱。

## 3. 下阶段优化实施路径（针对第一层）

基于上述理念，目前第一层图谱将进行以下轻量级演进：
1. **引入控辩与情节实体**：新增 `LitigationClaim`（控辩主张）和 `LegalCircumstance`（量刑/裁判情节），补全“主张 -> 焦点 -> 裁判”的逻辑链。
2. **角色扩展与标的属性化**：扩充 `LegalRole` 枚举以兼容相关参与人（如“其他相关人员”），并在 `CaseSummary` 强化 `target_object`（涉案标的）和 `financial_impact`（涉案金额）属性。
3. **补充通用关联边**：新增 `involved_in_fact`（主体卷入事实）和 `responds_to_claim`（法院回应主张）关系，解决事实网络和诉辩网络的断链问题。

# 主图本体与Neo4j一致性工程化调整方案

## 目标

- 统一 `Workspace` 主图、本体论结构、Neo4j `base` 图数据，消除“主图节点存在但本体未建模、Neo4j 未落库”的分叉。
- 形成单一真源：
  - 本体定义什么实体与关系
  - 解析输出就产出什么结构
  - `Workspace` 主图就渲染什么节点与边
  - Neo4j `base` 就写入什么标签与关系
  - `Database` diff / resync / subgraph 就校验什么内容

## 当前问题

- `quality_analyzer` 已将 `CourtCase`、`CaseSummary`、`TrialOrganization` 视为本体对象，但 `Neo4j base` 实体集合尚未纳入它们。
- `Workspace` 主图仍使用 `cc_0`、`cc_1`、`trial_org_0`、`summary` 这类前端骨架节点或占位节点。
- 关系端点仍混用：
  - 正式实体 id
  - 案号字符串
  - 前端占位 id
- `Neo4j base` 写入只接受已建模实体，因此 `appeals_to`、`tried_by`、`submitted_for`、`has_fact` 等结构边会被部分过滤。

## 调整原则

- 不允许前端临时节点脱离本体存在。
- 不允许案号字符串直接作为图关系端点。
- 主图只渲染正式本体实体。
- 非本体内容只能作为属性或面板信息展示，不能绕过本体混入图谱。

## 正式本体调整

### 新增正式实体

- `CourtCase`
  - 来源：`output.court_cases`
  - 作用：承载一审 / 二审 / 再审案件实例
- `TrialOrganization`
  - 来源：由 `court_cases[].court` 归一化派生
  - 作用：承载审理机关

### 暂不升格实体

- `CaseSummary`
  - 第一阶段作为 `Document` / `CourtCase` 属性保留
  - 暂不作为 `Neo4j base` 图节点
  - 后续若确认需要参与推理、引用、chunk 对齐，再升格为实体

### 端点规则

- 图中关系端点必须使用正式实体 id。
- 案号字符串只保留为 `CourtCase.case_number` 属性。
- `trial_org_0`、`cc_0` 这类占位 id 仅允许作为归一化前的临时别名，不能进入最终图谱。

## 新增关系

- `Document -[:HAS_CASE_INSTANCE]-> CourtCase`
- `CourtCase -[:TRIED_BY]-> TrialOrganization`
- `CourtCase -[:APPEALS_TO]-> CourtCase`
- `CourtCase -[:HAS_FACT]-> Fact`
- `CourtCase -[:HAS_DISPUTE_FOCUS]-> DisputeFocus`
- `Evidence -[:SUBMITTED_FOR]-> CourtCase`
- `CourtCase -[:HAS_JUDGMENT_RESULT]-> JudgmentResult`

## 实施阶段

### 阶段1：后端本体与输出结构

- 为 `court_cases` 生成正式稳定 id
- 从 `court_cases[].court` 派生 `trial_organizations`
- 将案号字符串、`cc_*`、`trial_org_*` 归一化为正式实体 id
- 让 `relations / derived_relations` 统一引用正式实体 id

### 阶段2：Neo4j base 写入与 schema

- 新增 `CourtCase`、`TrialOrganization` 标签与唯一约束
- 将两类实体纳入 `build_entity_payloads()`
- 写入 `tried_by`、`appeals_to` 等结构边
- 保证 `base` 层结构边不再被过滤

### 阶段3：Workspace 主图统一

- 主图使用正式 `CourtCase.id` / `TrialOrganization.id`
- 去除依赖 `cc_0`、`trial_org_0` 的主图骨架逻辑
- `CaseSummary` 由节点改为属性/面板展示

### 阶段4：Database 对齐

- `diff-case`、`resync-case`、`case-subgraph` 纳入新标签
- 图数据库摘要与状态统计同步更新

### 阶段5：校验与收口

- 增加本体一致性校验
- 保证主图节点类型全部能在本体注册表中找到
- 禁止关系端点落回案号字符串

## 验收标准

- 主图中出现的每个节点都能映射到正式本体实体
- Neo4j `base` 中的实体标签与主图节点类型一致
- `appeals_to`、`tried_by`、`submitted_for` 能稳定落库
- `Database diff` 不再因前端骨架节点造成结构差异
- 重新写入同一案例后，`CourtCase` 与 `TrialOrganization` id 稳定不漂移

## 当前剩余差异

- 当前基础层的一致性差异，主要集中在以下标签数量：
  - `Evidence`
  - `JudgmentResult`
  - `LegalProvisionElement`
- 这些差异不是“未建模”，而是当前图主键与合并策略导致的数量收缩：
  - 同一业务语义被合并为一个图节点
  - 本地 JSON 仍保留多条原始记录
- 后续若要做到“本地数量 = 图库数量”，需要单独裁定这些类型的主键策略，决定：
  - 继续按语义合并
  - 还是改为逐条记录入图

## 2. 已实现内容

## 2.1 后端基础能力

- 已接入 Neo4j 配置，当前以根目录 `.env` 为准，后端可直接读取 `NEO4J_URI / NEO4J_USER / NEO4J_PASSWORD / NEO4J_DATABASE`
- 已实现 Neo4j 连接、schema 初始化、基础写入、状态查询、详情查询、差异查询、重同步、子图摘要查询
- 已实现基础层 `base`、检索层 `retrieval`、发现层 `discovery` 三层分开写入
- 已实现 `cases_index` 自动清理失效条目，避免 Database 页面选中后发现记录已不存在

对用户体验的影响：

- 现在图数据库不再只是“后端内部能力”，而是用户可点击、可观察状态、可重试同步的功能
- Database 页面之前遇到“索引里有案例但实际点开报不存在”的概率会降低
- 同一案例的 `base / retrieval / discovery` 不再混在一起，用户可以分别看到各层是否写入

对用户交互逻辑的影响：

- 用户在 Workspace 中触发的是“主动写入”
- 用户在 Database 中触发的是“查看状态、比对差异、重同步”
- 用户不需要理解 Neo4j 内部结构，也能通过页面上的状态标签知道当前案例是否已同步

你应该如何验证和测试：

- 调用 `GET /api/neo4j/health`，确认 Neo4j 连接正常
- 调用 `GET /api/cases?include_neo4j=1`，确认案例索引里有 `neo4j_sync_status`
- 选一个已保存案件，依次调用：
  - `POST /api/neo4j/diff-case`
  - `POST /api/neo4j/resync-case`
  - `GET /api/neo4j/case-status/<doc_id>`
  - `GET /api/neo4j/case/<doc_id>`
- 确认重同步后 `base / retrieval / discovery` 状态与预期一致

## 2.2 文本块切分与对齐

- 已在解析主链中加入 chunk 切分与结构对齐
- 当前会返回并缓存：
  - `text_chunks`
  - `source_alignment`
  - `chunking_meta`
  - `alignment_stats`
  - `alignment_unmatched_items`
- 当前仍然保持“整篇文书调用大模型”的解析方式，没有把 chunk 喂给 LLM

对用户体验的影响：

- 现有解析主图没有被打断
- 解析结果已经具备“未来可反查原文块”的底座能力
- 当前虽然还没有做强交互展示，但后续不需要再重构解析链就能继续往 GraphRAG 或证据溯源走

对用户交互逻辑的影响：

- 用户当前在页面上几乎感觉不到额外负担
- 这部分更多是为后续“点节点看来源文本”预埋能力

你应该如何验证和测试：

- 在 Workspace 执行一次解析
- 通过接口返回值或缓存数据确认出现 `text_chunks` 和 `source_alignment`
- 刷新页面后确认这些字段仍可从 `/api/test-data` 恢复

## 2.3 Workspace 页面接入

- 已在 Workspace 底部保存区加入 `写入 Neo4j`
- 已在检索资产区加入 `写入检索层`
- 已在知识发现区加入 `写入发现层`
- 已在底部状态区加入图数据库状态展示，当前显示三层：
  - 基础层
  - 检索层
  - 发现层

对用户体验的影响：

- 用户现在不需要离开 Workspace，就可以完成解析结果到 Neo4j 的写入闭环
- 交互路径更短，不需要手动找后端脚本或接口测试工具
- 状态信息从“黑盒”变成了“页面可见”，更容易知道当前到底有没有写进去

对用户交互逻辑的影响：

- `保存` 仍然负责写本地记录
- `写入 Neo4j` 负责写 `base`
- 检索资产区的 `写入检索层` 负责写 `retrieval`
- 知识发现区的 `写入发现层` 负责写 `discovery`
- 三者语义已区分，不会再把所有内容都混成一次保存动作

你应该如何验证和测试：

- 在 Workspace 完成一次解析后，点击 `写入 Neo4j`
- 确认底部状态从“未写入”变成“基础层已写入”
- 生成检索资产后点击 `写入检索层`
- 生成知识发现后点击 `写入发现层`
- 刷新页面后确认状态仍能自动恢复

## 2.4 Database 页面接入

- 已在 Database 右侧增加 `图数据库` Tab
- 已支持在案例库页面查看：
  - 图数据库状态
  - 三层摘要
  - 图层差异
  - 从图数据库重载
  - 重新同步当前案例
  - 子图摘要
- 已为顶部筛选增加 `图数据库状态`
- 已为案例列表增加“图数据库已同步 / 未同步”标签

对用户体验的影响：

- Database 页面不再只是静态浏览器，而是具备图数据库运维与校验能力
- 用户可以更快判断：哪些案例已经进库、哪些还没进库、差异大不大
- 出现状态异常时，用户可以直接在页面里重同步，不必回到 Workspace 或手动调接口

对用户交互逻辑的影响：

- Workspace 偏“生产与写入”
- Database 偏“查看、校验、重同步”
- 两个页面职责更清晰

你应该如何验证和测试：

- 打开 Database 页面，选中一个已保存案例
- 观察案例列表标签是否正确显示同步状态
- 进入 `图数据库` Tab，依次点击：
  - `从图数据库重载`
  - `查看图层差异`
  - `重新同步当前案例`
  - `查看子图摘要`
- 确认右侧卡片和状态文案会更新

## 2.5 discovery_history 持久化

- 之前 `discovery_history` 只存在前端 `localStorage`
- 现在已经接入：
  - `POST /api/save`
  - `GET /api/saved-case/<row_id>`
  - Workspace 刷新回填
  - Database 重同步发现层

对用户体验的影响：

- 知识发现结果不再只是“当前浏览器里看得到”
- 保存后的案件换机器、换页面、刷新后，也能重新拿回发现历史
- Database 页终于可以对 discovery 层做真正意义上的重同步

对用户交互逻辑的影响：

- 用户执行深度思考后，只要正常保存案件，发现历史就进入正式记录
- 之后在 Database 页可以重新把最新一条发现历史同步到 Neo4j

你应该如何验证和测试：

- 在 Workspace 生成至少一条 discovery 结果
- 点击保存
- 调用 `GET /api/saved-case/<row_id>`，确认有 `discovery_history`
- 再调用 `POST /api/neo4j/resync-case` 且包含 `discovery`
- 确认 Neo4j 中 discovery 层状态变为 `written`

## 3. 尚未实现内容

## 3.1 Database 页面直接使用 Neo4j 子图重建主图视图

当前状态：

- 已经有 `case-subgraph` 摘要接口
- 但 Database 图谱主视图仍然主要依赖本地保存数据和原有转换链
- 目前 `图数据库` Tab 里展示的是“摘要”，不是直接可操作的 Neo4j 子图视图

功能必要性：

- 如果后续要真正把 Database 页面变成“图数据库消费端”，就不能只看摘要卡
- 用户需要能直接基于 Neo4j 返回的节点和关系浏览、定位、筛选

简要技术方案：

- 后端继续复用 `GET /api/neo4j/case-subgraph/<doc_id>`
- 前端在 Database 页增加一个模式：
  - `本地视图`
  - `Neo4j 子图视图`
- 把子图接口返回的 `nodes / edges` 转成 `DatabaseGraph` 可直接消费的数据结构

对用户体验的影响：

- 用户可以确认“图数据库里现在到底长什么样”
- 更适合排查写库偏差，而不只是看数量统计

对用户交互逻辑的影响：

- 在 Database 页会多一个“切换视图来源”的动作
- 用户可以在同一案例下比较“本地结构图”和“Neo4j 子图”

## 3.2 discovery 层多记录管理

当前状态：

- 现在 Database 页重同步发现层时，使用的是“最新一条 discovery 记录”
- 还没有做“从多条历史记录中选择某一条或批量重放”

功能必要性：

- 如果未来一个案件会多轮深度思考，只有“最后一条”往往不够
- 用户可能需要对比不同 discovery 轮次的结论，或者只同步其中一轮

简要技术方案：

- `discovery_history` 保持数组结构
- Database 页增加 discovery 历史列表
- 重同步时允许：
  - 同步最新一条
  - 选择单条同步
  - 批量同步

对用户体验的影响：

- 用户能更精细地控制 discovery 写库，不会被迫只接受最后一条

对用户交互逻辑的影响：

- `图数据库` Tab 里会增加 discovery 历史选择器
- `重新同步当前案例` 可能拆成“同步最新 / 选择同步”

## 3.3 Neo4j 子图与前端本地图谱的差异可视化

当前状态：

- 已有数量级 diff
- 还没有做到“具体哪些节点、哪些关系缺失或多出”的可视化差异

功能必要性：

- 当前 diff 更适合判断“有无问题”
- 如果要真正定位问题，仍然不够细

简要技术方案：

- 后端增加更细粒度的 diff：
  - 本地节点 ID 集合
  - Neo4j 节点 ID 集合
  - 本地关系 ID 集合
  - Neo4j 关系 ID 集合
- 前端在 Database 页提供：
  - 缺失节点列表
  - 多出节点列表
  - 缺失关系列表
  - 多出关系列表

对用户体验的影响：

- 用户能从“知道不一致”提升到“知道哪里不一致”

对用户交互逻辑的影响：

- `查看图层差异` 将从摘要卡扩展成可展开的明细视图

## 3.4 retrieval / discovery 的 Database 页面专项浏览

当前状态：

- `retrieval` 和 `discovery` 已可写库、可查状态
- 但 Database 页对这两层仍以摘要为主

功能必要性：

- 未来如果类案检索、规则学习越来越依赖这两层，就需要独立浏览它们的结构

简要技术方案：

- 在 `图数据库` Tab 中增加 layer 切换：
  - `base`
  - `retrieval`
  - `discovery`
- 对每层分别拉子图摘要或完整子图

对用户体验的影响：

- 用户能直接把基础事实图、检索资产图、发现图分开看

对用户交互逻辑的影响：

- `图数据库` Tab 会从单页卡片扩展成“分层浏览区”

## 3.5 GraphRAG / 向量化 / 实体相似合并

当前状态：

- 当前没有启用向量化
- 也还没有把相似文本节点做真正的向量合并
- GraphRAG 查询链也还没有进入实施

功能必要性：

- 这是后续跨案检索、相似事实合并、知识发现扩展的关键能力
- 没有这一步，Neo4j 目前更偏结构化存储与状态管理，而不是完整的 GraphRAG 平台

简要技术方案：

- 保持当前 Neo4j 图结构不变
- 在后端引入 embedding 生成服务
- 先做同案相似节点合并，再做跨案相似检索
- 最后再接 GraphRAG 的“向量召回 + 图扩展 + LLM 总结”

对用户体验的影响：

- 用户能从“看单案图谱”提升到“做类案检索、做图谱问答、做结构化证据发现”

对用户交互逻辑的影响：

- Workspace 可能增加“相似节点合并确认”
- Database 页面可能增加“图谱问答 / 类案图扩展”

## 3.6 图数据库生产级能力

当前状态：

- 当前用的是开发态 Flask 服务和手工重同步路径
- 已足够支撑当前验证，但还不算生产级方案

功能必要性：

- 后续如果要进入更高并发、更高数据量，就需要更稳定的任务化能力

简要技术方案：

- 引入 MQ 或任务队列
- 引入批量写入优化
- 引入更正式的日志、重试、失败队列、告警
- 引入定时校验与索引修复工具

对用户体验的影响：

- 普通用户层面变化不大
- 但系统稳定性、可恢复性、数据一致性会明显提升

对用户交互逻辑的影响：

- 前端可能会从“立即写入”扩展成“提交写入任务 -> 查看任务状态”

## 4. 当前推荐验证路径

如果你现在要快速确认“当前版本到底能不能用”，建议按下面顺序测：

1. Workspace 测试
   - 解析一篇案件
   - 点击 `保存`
   - 点击 `写入 Neo4j`
   - 如果有检索资产，点击 `写入检索层`
   - 如果有知识发现，点击 `写入发现层`

2. Database 测试
   - 刷新 Database 页面
   - 观察案例列表中的同步状态标签
   - 进入 `图数据库` Tab
   - 依次点：
     - `从图数据库重载`
     - `查看图层差异`
     - `重新同步当前案例`
     - `查看子图摘要`

3. discovery 持久化测试
   - 在 Workspace 生成 discovery
   - 保存案件
   - 调用 `GET /api/saved-case/<row_id>`
   - 确认返回 `discovery_history`
   - 再去 Database 页重同步 discovery 层

## 5. 总结

当前阶段已经完成的不是“一个概念验证 demo”，而是一套可实际操作的 Neo4j 接入闭环：

- Workspace 可写
- Database 可看、可 diff、可重同步
- discovery 已可持久化并重放
- 索引脏数据问题已有自动修正

尚未实现的内容，主要集中在两个方向：

- 把 Neo4j 子图真正变成前端主视图的一部分
- 把 GraphRAG、向量化、相似合并这些高级能力继续接上

因此，当前系统已经可以用于：

- 单案图谱写入验证
- 三层图数据状态管理
- 前后端协同联调
- Neo4j 接入链路的持续迭代

但如果要进入“真正以图数据库为核心消费层”的下一阶段，还需要继续补完子图直接渲染、细粒度差异可视化和 GraphRAG 能力。

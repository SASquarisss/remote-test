## 2.3 最佳挂接策略

基于当前代码结构，Neo4j 的挂接策略建议如下：

### 后端

#### 第 1 批挂接点

1. `parser.py::parse_text()`
   - 加入 chunk 切分与结构对齐

2. `app.py::api_parse()`
   - 可选择返回 `text_chunks` 和 `source_alignment`

3. `app.py::_save_test_data() / _patch_test_data()`
   - 扩展缓存结构，允许保留 chunk 与图数据库状态

4. `app.py::api_save()`
   - 保持原逻辑
   - 预留双写或后续手动写库调用

#### 第 2 批挂接点

1. 新增 Neo4j 写入接口
2. 新增 Neo4j 状态查询接口
3. 新增 Neo4j 差异接口
4. 新增 Neo4j 读案例详情接口

### 前端

#### Workspace

1. 在 `handleSave()` 所在按钮区新增“写入 Neo4j”
2. 在 Retrieval 操作区新增“写入检索层”
3. 在 Discovery 操作区新增“写入发现层”
4. 在状态栏增加“图数据库状态”提示

#### Database

1. 右侧新增 `图数据库` Tab
2. 增加案例同步状态查看
3. 增加“从图数据库重载 / 重新同步 / 查看差异”

## 4. 数据对象与字段字典

本节定义建议的“传输对象”。

## 4.1 文书上下文 `DocContext`

```json
{
  "row_id": "manual_1710000000",
  "doc_id": "CASE:2024-001",
  "doc_type": "case",
  "external_id": "2024-001",
  "case_name": "某某纠纷案",
  "source": "manual",
  "source_text_hash": "sha256_xxx"
}
```

字段说明：

- `row_id`：当前本地工作台记录 ID
- `doc_id`：写入图数据库时使用的文书主键
- `doc_type`：`case | guiding_case`
- `external_id`：上游提供的原始唯一 ID
- `case_name`：案件名称
- `source`：`manual | extracted_candidate | static`
- `source_text_hash`：用于检测是否是同一份原文

## 4.2 工作台上下文 `WorkspaceContext`

```json
{
  "workspace_id": "workspace_default",
  "active_tab": "termJsonArea",
  "selected_graph": "parse",
  "parse_active_version_id": "v2",
  "operator": "user"
}
```

字段说明：

- `workspace_id`：后续支持工作区隔离
- `active_tab`：前端当前 tab
- `selected_graph`：当前选中的图类型
- `parse_active_version_id`：当前激活解析版本
- `operator`：可先固定为 `user`

## 4.3 文本块对象 `ChunkDTO`

```json
{
  "chunk_id": "CASE:2024-001:basic_facts:003",
  "doc_id": "CASE:2024-001",
  "section_type": "basic_facts",
  "seq": 3,
  "text": "……",
  "char_start": 1820,
  "char_end": 2016,
  "paragraph_index": 7,
  "chunking_version": "v1"
}
```

字段约束：

- `chunk_id`：必填，全局唯一
- `section_type`：必填，如 `basic_facts` / `judgment_reason`
- `seq`：必填，文书内顺序
- `text`：必填，原文片段
- `char_start` / `char_end`：建议保留，便于高亮与校验

## 4.4 对齐对象 `AlignmentDTO`

```json
{
  "node_key": "Fact:abc123",
  "matches": [
    {
      "chunk_id": "CASE:2024-001:basic_facts:003",
      "match_type": "contains",
      "score": 1.0
    }
  ]
}
```

字段说明：

- `node_key`：建议为 `Type:entity_id`
- `matches`：允许一对多
- `match_type`：`contains | normalized_contains | fuzzy | section_fallback`
- `score`：规则评分，范围 `0-1`

## 4.5 图写入选项 `GraphWriteOptions`

```json
{
  "graph_layer": "base",
  "include_chunks": true,
  "overwrite_scope": "doc_layer",
  "create_run": true,
  "force_reingest": false,
  "write_mode": "manual_click"
}
```

字段说明：

- `graph_layer`：`base | retrieval | discovery | community`
- `include_chunks`：是否写入 chunk
- `overwrite_scope`：`doc_layer | none`
- `create_run`：是否为本次写入生成 `IngestRun`
- `force_reingest`：是否允许强制覆盖
- `write_mode`：`manual_click | save_hook | database_panel | mq_consumer`

## 5. API 设计细化

## 5.1 解析相关

## 5.1.1 方案 A：扩展现有 `/api/parse`

推荐程度：高

原因：

- 不新增调用入口
- 对前端改动最小
- 与现有 `handleParse()` 兼容性最好

建议请求：

`POST /api/parse`

```json
{
  "text": "原始裁判文书全文",
  "options": {
    "include_chunks": true,
    "include_alignment": true
  }
}
```

建议响应：

```json
{
  "row_id": "manual_1710000000",
  "case_name": "某某纠纷案",
  "json_result": {},
  "nodes": [],
  "edges": [],
  "score": 88,
  "issues": [],
  "text_chunks": [],
  "source_alignment": {},
  "chunking_meta": {
    "version": "v1",
    "chunk_count": 18
  }
}
```

后端处理建议：

1. 如果 `options.include_chunks != true`，保持老行为
2. 如果启用，则：
   - `parse_text()` 返回新增字段
   - `_save_test_data()` 也保存这些字段

## 5.1.2 方案 B：新增 `/api/parse-with-chunks`

推荐程度：中

优点：

- 旧接口无风险

缺点：

- 前端需要引入第二套解析入口
- 同一业务有双接口，后续维护成本更高

结论：

- 优先方案 A

## 5.2 Neo4j 写入接口

## 5.2.1 `POST /api/neo4j/write-case`

### 用途

- 写入文书、chunk、基础解析图

### 请求体

```json
{
  "doc_context": {
    "row_id": "manual_1710000000",
    "doc_id": "CASE:2024-001",
    "doc_type": "case",
    "external_id": "2024-001",
    "case_name": "某某纠纷案",
    "source": "manual",
    "source_text_hash": "sha256_xxx"
  },
  "workspace_context": {
    "workspace_id": "workspace_default",
    "active_tab": "termJsonArea",
    "selected_graph": "parse",
    "parse_active_version_id": "v2",
    "operator": "user"
  },
  "data": {
    "raw_text": "……",
    "json_result": {},
    "parse_versions": [],
    "active_version_id": "v2",
    "text_chunks": [],
    "source_alignment": {}
  },
  "write_options": {
    "graph_layer": "base",
    "include_chunks": true,
    "overwrite_scope": "doc_layer",
    "create_run": true,
    "force_reingest": false,
    "write_mode": "manual_click"
  }
}
```

### 后端校验规则

必填：

- `doc_context.doc_id`
- `doc_context.doc_type`
- `data.json_result`
- `write_options.graph_layer`

约束：

- `graph_layer` 必须为 `base`
- `doc_type` 必须为 `case | guiding_case`
- `overwrite_scope` 允许值：`doc_layer | none`

### 响应体

```json
{
  "status": "ok",
  "doc_id": "CASE:2024-001",
  "graph_layer": "base",
  "source_run_id": "ingest_20260618_001",
  "write_summary": {
    "document_written": true,
    "chunk_count": 18,
    "node_count": 128,
    "relation_count": 241,
    "deactivated_count": 12
  },
  "neo4j_status": {
    "base": "written",
    "retrieval": "unknown",
    "discovery": "unknown"
  }
}
```

### 错误码建议

- `400`：参数缺失
- `409`：文书主键冲突且不允许覆盖
- `422`：`json_result` 无法映射为图对象
- `500`：Neo4j 写入失败

## 8. Neo4j 图模型落地草案

## 8.1 标签与主键

### 8.1.1 控制层

| 标签 | 主键 | 说明 |
|---|---|---|
| `Document` | `doc_id` | 一篇文书一个根节点 |
| `Chunk` | `chunk_id` | 文本块 |
| `ParseRun` | `run_id` | 一次解析 |
| `IngestRun` | `run_id` | 一次图写入 |

### 8.1.2 结构层

| 标签 | 主键 |
|---|---|
| `Organization` | `id` |
| `Person` | `id` |
| `Fact` | `id` |
| `Evidence` | `id` |
| `ArgumentPoint` | `id` |
| `JudicialAssessment` | `id` |
| `LitigationClaim` | `id` |
| `ProceduralOpinion` | `id` |
| `JudgmentResult` | `id` |
| `LegalProvision` | `id` |
| `CaseType` | `id` |

## 8.2 关系落地规则

### 文书与 chunk

```text
(:Document)-[:HAS_CHUNK]->(:Chunk)
```

### 文书与结构节点

```text
(:Document)-[:HAS_ENTITY {graph_layer, source_run_id}]->(:Fact)
(:Document)-[:HAS_ENTITY {graph_layer, source_run_id}]->(:Evidence)
...
```

### 结构节点与 chunk

```text
(:Fact)-[:SUPPORTED_BY_CHUNK {score, match_type}]->(:Chunk)
(:Evidence)-[:SUPPORTED_BY_CHUNK {score, match_type}]->(:Chunk)
```

### 结构节点之间

```text
(:Evidence)-[:PROVES {relation_origin}]->(:Fact)
(:ArgumentPoint)-[:SUPPORTS]->(:LitigationClaim)
(:JudicialAssessment)-[:RESPONDS_TO]->(:ArgumentPoint)
(:JudgmentResult)-[:CITES_PROVISION]->(:LegalProvision)
```

### 运行与来源

```text
(:Entity)-[:GENERATED_BY_PARSE_RUN]->(:ParseRun)
(:Entity)-[:INGESTED_BY]->(:IngestRun)
```

## 9. Cypher 草案

以下 Cypher 是设计草案，不保证可直接执行，但其结构可直接作为实现蓝本。

## 9.1 创建约束

```cypher
CREATE CONSTRAINT document_doc_id IF NOT EXISTS
FOR (n:Document) REQUIRE n.doc_id IS UNIQUE;

CREATE CONSTRAINT chunk_chunk_id IF NOT EXISTS
FOR (n:Chunk) REQUIRE n.chunk_id IS UNIQUE;

CREATE CONSTRAINT parse_run_id IF NOT EXISTS
FOR (n:ParseRun) REQUIRE n.run_id IS UNIQUE;

CREATE CONSTRAINT ingest_run_id IF NOT EXISTS
FOR (n:IngestRun) REQUIRE n.run_id IS UNIQUE;

CREATE CONSTRAINT organization_id IF NOT EXISTS
FOR (n:Organization) REQUIRE n.id IS UNIQUE;

CREATE CONSTRAINT fact_id IF NOT EXISTS
FOR (n:Fact) REQUIRE n.id IS UNIQUE;

CREATE CONSTRAINT evidence_id IF NOT EXISTS
FOR (n:Evidence) REQUIRE n.id IS UNIQUE;

CREATE CONSTRAINT argument_point_id IF NOT EXISTS
FOR (n:ArgumentPoint) REQUIRE n.id IS UNIQUE;

CREATE CONSTRAINT judicial_assessment_id IF NOT EXISTS
FOR (n:JudicialAssessment) REQUIRE n.id IS UNIQUE;

CREATE CONSTRAINT legal_provision_id IF NOT EXISTS
FOR (n:LegalProvision) REQUIRE n.id IS UNIQUE;
```

## 9.2 Upsert 文书

```cypher
MERGE (d:Document {doc_id: $doc_id})
ON CREATE SET
  d.doc_type = $doc_type,
  d.external_id = $external_id,
  d.case_name = $case_name,
  d.source = $source,
  d.source_text_hash = $source_text_hash,
  d.created_at = datetime($now),
  d.updated_at = datetime($now)
ON MATCH SET
  d.case_name = $case_name,
  d.source_text_hash = $source_text_hash,
  d.updated_at = datetime($now);
```

## 9.3 Upsert chunk

```cypher
MATCH (d:Document {doc_id: $doc_id})
MERGE (c:Chunk {chunk_id: $chunk_id})
ON CREATE SET
  c.doc_id = $doc_id,
  c.section_type = $section_type,
  c.seq = $seq,
  c.text = $text,
  c.char_start = $char_start,
  c.char_end = $char_end,
  c.paragraph_index = $paragraph_index,
  c.chunking_version = $chunking_version,
  c.created_at = datetime($now),
  c.updated_at = datetime($now)
ON MATCH SET
  c.text = $text,
  c.updated_at = datetime($now)
MERGE (d)-[:HAS_CHUNK]->(c);
```

## 9.4 Upsert 基础层实体

```cypher
MATCH (d:Document {doc_id: $doc_id})
MERGE (n:Fact {id: $id})
ON CREATE SET
  n.doc_id = $doc_id,
  n.content = $content,
  n.fact_type = $fact_type,
  n.graph_layer = 'base',
  n.source_pipeline = $source_pipeline,
  n.source_run_id = $source_run_id,
  n.version_id = $version_id,
  n.active_flag = true,
  n.created_at = datetime($now),
  n.updated_at = datetime($now)
ON MATCH SET
  n.content = $content,
  n.fact_type = $fact_type,
  n.source_run_id = $source_run_id,
  n.version_id = $version_id,
  n.active_flag = true,
  n.updated_at = datetime($now)
MERGE (d)-[:HAS_ENTITY {
  graph_layer: 'base',
  source_run_id: $source_run_id
}]->(n);
```

## 9.5 Upsert 实体到 chunk 的溯源关系

```cypher
MATCH (n {id: $entity_id})
MATCH (c:Chunk {chunk_id: $chunk_id})
MERGE (n)-[r:SUPPORTED_BY_CHUNK {chunk_id: $chunk_id}]->(c)
ON CREATE SET
  r.score = $score,
  r.match_type = $match_type,
  r.created_at = datetime($now),
  r.updated_at = datetime($now)
ON MATCH SET
  r.score = $score,
  r.match_type = $match_type,
  r.updated_at = datetime($now);
```

## 9.6 逻辑失活旧层关系

如果采用“按 doc_id + graph_layer 覆盖”的策略，则写入前先失活旧关系：

```cypher
MATCH (d:Document {doc_id: $doc_id})-[r:HAS_ENTITY]->(n)
WHERE r.graph_layer = $graph_layer
SET r.active_flag = false,
    r.deactivated_at = datetime($now);
```

## 10. 读写状态流

## 10.1 Workspace 基础层写入状态流

```text
解析完成
  -> 前端拿到 json_result / parseVersions / text_chunks
  -> 用户点击“写入 Neo4j”
  -> POST /api/neo4j/write-case
  -> 后端校验 doc_context / json_result / graph_layer
  -> 生成 IngestRun
  -> Upsert Document
  -> Upsert Chunk
  -> 映射 json_result 为图节点 / 关系
  -> Upsert Base Layer
  -> 写入溯源关系
  -> 返回写入摘要
  -> 前端更新 neo4jStatus
```

## 10.2 Retrieval 层写入状态流

```text
用户点击“生成检索资产”
  -> /api/retrieval/build
  -> 用户编辑 / 保存 / 重新向量化 / 文件写出
  -> 用户点击“写入检索层”
  -> /api/neo4j/write-retrieval-layer
  -> 后端映射 retrieval_bundle
  -> Upsert retrieval layer
  -> 前端刷新 neo4jStatus.retrieval
```

## 10.3 Discovery 层写入状态流

```text
用户点击“深度思考”
  -> /api/deep-think (SSE)
  -> 前端解析 reasoning + JSON
  -> 形成 discoveryHistory 条目
  -> 用户点击“写入发现层”
  -> /api/neo4j/write-discovery-layer
  -> 后端映射 virtual_nodes / relations / patch
  -> Upsert discovery layer
  -> 前端刷新 neo4jStatus.discovery
```

## 12. 风险控制与回滚策略

## 12.1 不替换现有 JSONL

这是第一条底线：

- Neo4j 引入初期不废弃本地 JSONL
- JSONL 仍然是调试与人工核验底座

## 12.2 不让 Workspace 默认从图数据库读

这是第二条底线：

- 当前 Workspace 仍是编辑态工作台
- 默认读图数据库会引入未保存态冲突

## 12.3 先失活，后删除

这是第三条底线：

- 对旧图层数据优先逻辑失活
- 避免早期误删导致数据不可恢复

## 12.4 企业名称合并保持保守

这是第四条底线：

- 没有统一社会信用代码前，不做过强公司实体跨案合并

## 13. 实施完成后的最低可用标准

满足以下条件，就可认为 Neo4j 第一阶段落地成功：

1. `POST /api/parse` 可返回 chunk 与 alignment
2. `POST /api/neo4j/write-case` 可写入基础图谱
3. Workspace 有 `写入 Neo4j` 按钮
4. 可以查询某个 `doc_id` 的写入状态
5. Neo4j 中能看到：
   - `Document`
   - `Chunk`
   - 至少一类基础节点，如 `Fact`
   - 节点与 chunk 的溯源关系
6. 不影响当前：
   - 解析
   - 保存
   - 检索资产
   - 深度思考
   - 版本链

## 14. 结论

如果把上一份文档视为“要做什么”，那么本文档已经把它进一步细化成了“具体在哪改、接口怎么定、图怎么落、状态怎么流、任务怎么拆”。

建议实际实施时按以下顺序推进：

1. 先做 `parse_text()` 扩展与 chunk / alignment
2. 再做 `write-case`
3. 再做 Workspace 基础层写入按钮
4. 再扩 retrieval / discovery 图层
5. 最后把 Database 逐步接到 Neo4j

这样能保证：

- 改动是渐进式的
- 现有工作台不中断
- 每一步都有清晰验收点
- 后续 GraphRAG 扩展不会推翻现有设计
